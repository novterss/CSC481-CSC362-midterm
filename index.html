CSC362 • ข้อที่ 4 (15 คะแนนเต็ม)

Normalization Masterclass (UNF -> 1NF -> 2NF -> 3NF)

ขั้นตอนมาตรฐานในการแตกตารางเพื่อกำจัดความซ้ำซ้อนและ Anomaly (Insert, Update, Delete)

ขั้นตอนที่ 1: ทำ 1NF

กำจัด Repeating Groups & กำหนด Primary Key

• ในเอกสารบิล/ใบเสร็จ 1 ใบ จะมีรายการสินค้าหลายรายการ ทำให้เกิดข้อมูลซ้ำซ้อน
• วิธีทำ 1NF: แตกให้ทุกรายการสินค้าเป็น 1 แถวแยกเดี่ยว และกำหนด Composite Primary Key ร่วมกันระหว่าง OrderID + ProductID

1NF Relation:
ORDER_1NF (OrderID, OrderDate, CustomerID, CustomerName, CustomerAddress, ProductID, ProductName, UnitPrice, Quantity)
ขั้นตอนที่ 2: ทำ 2NF

กำจัด "Partial Dependency" (ความขึ้นต่อคีย์หลักเพียงบางส่วน)

ความหมายของ Partial Dependency: เมื่อ Primary Key เป็น Composite Key (เช่น OrderID + ProductID) แต่มีฟิลด์อื่นไปขึ้นตรงกับแค่ตัวใดตัวหนึ่ง เช่น:
• OrderID -> OrderDate, CustomerID, CustomerName, CustomerAddress (ไม่เกี่ยวกับ ProductID เลย!)
• ProductID -> ProductName, UnitPrice (ไม่เกี่ยวกับ OrderID เลย!)
• OrderID, ProductID -> Quantity (อันนี้ Full Dependency ผ่าน!)

วิธีแก้: แตกออกเป็น 3 ตารางเพื่อดึงฟิลด์ที่ขึ้นกับคีย์บางส่วนออกไป:

2NF Tables:
1. ORDER (OrderID, OrderDate, CustomerID, CustomerName, CustomerAddress)
2. PRODUCT (ProductID, ProductName, UnitPrice)
3. ORDER_DETAIL (OrderID*, ProductID*, Quantity)
ขั้นตอนที่ 3: ทำ 3NF (ขั้นตอนสุดท้าย ได้คะแนนเต็ม!)

กำจัด "Transitive Dependency" (ความขึ้นต่อกันระหว่างฟิลด์ที่ไม่ใช่คีย์)

ความหมายของ Transitive Dependency (A -> B -> C):
ดูที่ตาราง ORDER: ฟิลด์ OrderID (คีย์) -> CustomerID (ฟิลด์ธรรมดา) -> CustomerName, CustomerAddress (ฟิลด์ธรรมดา)
*CustomerName และ Address มันไม่ได้ขึ้นตรงกับ OrderID แต่ขึ้นกับ CustomerID ต่างหาก!*

วิธีแก้: ดึง CustomerID และข้อมูลลูกค้าแยกไปเป็นตาราง CUSTOMER ต่างหาก:

3NF Tables (สมบูรณ์ 100%):
1. CUSTOMER (CustomerID, CustomerName, CustomerAddress)
2. ORDER (OrderID, OrderDate, CustomerID*)
3. PRODUCT (ProductID, ProductName, UnitPrice)
4. ORDER_DETAIL (OrderID*, ProductID*, Quantity)
ทริคตอบข้อสอบให้ได้คะแนนเต็ม:
1. ขีดเส้นใต้ (Underline) ใต้ Primary Key ทุกตัว
2. ใส่เครื่องหมายดอกจัน * หรือเขียนกำกับ (FK) ชัดเจน
3. ตั้งชื่อตารางให้สื่อความหมาย (Meaningful name)

🏷️ ชนิดของ Attributes ในข้อสอบ

A
ประเภทสัญลักษณ์ตัวอย่าง
Simple / Atomicวงรีเส้นเดี่ยวSalary, Gender

🏢 Strong vs Weak Entity

B

• Strong Entity (เอนทิตีปกติ): อยู่ได้ด้วยตัวเอง มี Primary Key ของตนเอง เช่น EMPLOYEE, STUDENT (วาดกรอบสี่เหลี่ยมเส้นเดี่ยว)


• Weak Entity (เอนทิตีอ่อนแอ): อยู่คนเดียวไม่ได้ ต้องพึ่งพาการมีอยู่ของ Strong Entity (Existence Dependent) และไม่มี Primary Key ที่สมบูรณ์ในตัวเอง ต้องยืม PK ของตัวแม่มาร่วมเป็น Partial Key เช่น DEPENDENT (ข้อมูลบุตรของพนักงาน) (วาดกรอบสี่เหลี่ยมเส้นคู่ Double Rectangle)

การแปลง ER Diagram เป็น Relational Schema (Tables)

กฎตายตัว 3 ข้อในการแปลงความสัมพันธ์ 1:1, 1:M, M:N ให้ได้ตารางที่ถูกต้อง

1 : M (หนึ่งต่อกลุ่ม)

1

สถานการณ์: แผนก 1 แผนก มีพนักงานได้หลายคน แต่พนักงาน 1 คนสังกัดได้แผนกเดียว

กฎเหล็ก: เอา Primary Key ของ ฝั่ง 1 ไปเป็น Foreign Key ใน ฝั่ง M เสมอ!
DEPARTMENT (DeptNo, DeptName)

EMPLOYEE (EmpID, EmpName, DeptNo*)

M : N (กลุ่มต่อกลุ่ม)

2

สถานการณ์: นักศึกษา 1 คน ลงเรียนได้หลายวิชา, 1 วิชา มีนักศึกษาเรียนได้หลายคน

กฎเหล็ก: แตกตารางตรงกลาง (Bridge Table) โดยดึง PK ของทั้ง 2 ฝั่งมารวมกันเป็น Composite PK!
STUDENT (StudentID, Name)
COURSE (CourseID, Title)

ENROLL (StudentID*, CourseID*, Grade)

1 : 1 (หนึ่งต่อหนึ่ง)

3

สถานการณ์: พนักงาน 1 คน มีที่จอดรถส่วนตัว 1 ช่อง (1 ช่องเป็นของพนักงานคนเดียว)

กฎเหล็ก: เอา PK ฝั่งใดฝั่งหนึ่งไปเป็น FK ในอีกฝั่ง โดยเลือกฝั่งที่จำเป็นต้องมีข้อมูลเพื่อเลี่ยงค่า NULL
EMPLOYEE (EmpID, EmpName)

PARKING_SPACE (SpaceID, Location, EmpID*)

คลังความรู้เรื่อง Keys & Relational Integrity

ประเภทของ Key และกฎควบคุมความถูกต้องของฐานข้อมูลเชิงสัมพันธ์

🔑 สรุปสาระสำคัญเรื่อง Keys

Key
  • • Superkey: ฟิลด์หรือกลุ่มฟิลด์ใดๆ ที่ระบุแต่ละแถวได้ไม่ซ้ำกัน
  • • Candidate Key: Superkey ขั้นต่ำสุด (Minimal Superkey) ที่ไม่มีฟิลด์ส่วนเกิน ทุกตัวมีสิทธิ์เป็น Primary Key ได้
  • • Primary Key (PK): Candidate Key ที่ถูกเลือกขึ้นมาเป็นตัวแทนระบุแถวอย่างเป็นทางการ (ต้อง NOT NULL & UNIQUE)
  • • Composite Key: Primary Key ที่ประกอบด้วย 2 แอตทริบิวต์ขึ้นไป
  • • Foreign Key (FK): แอตทริบิวต์ที่ใช้เชื่อมโยง โดยไปอ้างอิงถึง Primary Key ของอีกตารางหนึ่ง

🛡️ Relational Integrity Constraints

Rule
1. Entity Integrity (ความถูกต้องของเอนทิตี):
Primary Key จะต้อง **ห้ามเป็นค่าว่าง (NOT NULL)** และห้ามซ้ำกันโดยเด็ดขาด เพราะถ้าเป็น NULL จะไม่สามารถระบุตัวตนของแถวข้อมูลได้
2. Referential Integrity (ความถูกต้องของการอ้างอิง):
ค่าใน Foreign Key จะต้อง **ตรงกับค่า Primary Key ในตารางแม่ที่มีอยู่จริง** หรือเป็นค่า NULL (หากความสัมพันธ์นั้นเป็นแบบ Optional)

SDLC 5 ขั้นตอน & Waterfall vs Agile

วงจรการพัฒนาระบบสารสนเทศ และการเปรียบเทียบวิธีการพัฒนายอดนิยม

🌊 Waterfall Model (แบบดั้งเดิม)

W

• ลักษณะ: ทำงานเป็นขั้นบันไดทีละขั้น เฟสก่อนหน้าต้องเสร็จ 100% ถึงจะเริ่มเฟสถัดไปได้
• ข้อดี: วางแผนชัดเจน ควบคุมเอกสารและงบประมาณได้ง่าย เหมาะกับโปรเจกต์ที่ Requirement นิ่ง ไม่เปลี่ยน
• ข้อเสีย: ไม่ยืดหยุ่น ถ้าลูกค้าเปลี่ยน Requirement กลางคันจะแก้ยากมาก และเห็นระบบตอนปลายสุดเท่านั้น

⚡ Agile Methodologies (แบบสมัยใหม่)

A

• ลักษณะ: แบ่งการทำงานเป็นรอบสั้นๆ เรียกว่า Sprint (1-4 สัปดาห์) มีการส่งมอบชิ้นงานที่ใช้งานได้จริงในทุกรอบ
• ข้อดี: ยืดหยุ่นสูง รับมือกับการเปลี่ยนแปลงได้ดี ลูกค้าเห็นงานตลอดเวลา
• ข้อเสีย: ควบคุม Scope และงบประมาณสุดท้ายได้ยาก หากไม่มีวินัยอาจเกิด Scope Creep ได้ง่าย

Feasibility 4 ด้าน & SWOT/TOWS Matrix

การศึกษาความเป็นไปได้และการจับคู่กลยุทธ์ตามสไลด์เคสศึกษา 7-Eleven

🔍 Feasibility Study (ความเป็นไปได้ 4 ด้าน)

4
  • • 1. Economic Feasibility: ความคุ้มค่าทางการเงิน (Cost-Benefit Analysis, TCO, ROI, Payback Period)
  • • 2. Technical Feasibility: เทคโนโลยีและฮาร์ดแวร์/ทีมงานมีความพร้อมรองรับได้หรือไม่
  • • 3. Operational Feasibility: ระบบใหม่เข้ากับการทำงานของคนในองค์กรและแก้ปัญหาได้จริงไหม
  • • 4. Schedule Feasibility: สามารถพัฒนาระบบให้เสร็จทันเวลาที่กำหนดได้หรือไม่

🎯 TOWS Matrix (การจับคู่กลยุทธ์)

T
กลยุทธ์เชิงรุก (S + O): ใช้จุดแข็ง วิ่งเข้าหาโอกาสที่เปิดอยู่เพื่อเติบโตก้าวกระโดด
กลยุทธ์เชิงแก้ไข (W + O): พยายามปิดจุดอ่อนภายใน เพื่อไม่ให้เสียโอกาสสำคัญภายนอกไป
กลยุทธ์เชิงป้องกัน (S + T): ใช้จุดแข็งเป็นเกราะป้องกันภัยคุกคามจากภายนอก
กลยุทธ์เชิงรับ (W + T): ลดความเสี่ยงที่เลวร้ายที่สุด (จุดที่จุดอ่อนตรงกับภัยคุกคามพอดี)

Data Flow Diagram (DFD) & กฎเหล็ก 3 ข้อ

การจำลองการไหลของข้อมูลและข้อผิดพลาดร้ายแรงที่ห้ามวาดในห้องสอบ

🕳️ Black Hole (หลุมดำ)

!
อาการ: Process มีแต่ลูกศรข้อมูลไหลเข้า (Inputs) แต่ไม่มีข้อมูลไหลออก (Outputs) เลยแม้แต่เส้นเดียว!

เหมือนโยนข้อมูลลงหลุมดำ ระบบประมวลผลแล้วไม่ส่งผลลัพธ์ให้ใครเลย ถือว่าผิดกฎทันที!

✨ Miracle (ปาฏิหาริย์)

!
อาการ: Process มีลูกศรข้อมูลไหลออก (Outputs) แต่ไม่มีข้อมูลไหลเข้า (Inputs) เลย!

จู่ๆ ระบบก็เสกข้อมูลส่งออกไปเองได้โดยไม่รับข้อมูลต้นทางเข้ามา ถือเป็นปาฏิหาริย์ที่ผิดหลักการ

🌫️ Gray Hole (หลุมเทา)

!
อาการ: ข้อมูลขาเข้าไม่สมเหตุสมผลหรือไม่เพียงพอที่จะสร้างข้อมูลขาออกได้

เช่น รับข้อมูลเข้ามาแค่ "ชื่อสินค้า" แต่ขาส่งออกดันสร้าง "ใบแจ้งยอดรวมภาษี" ได้ ซึ่งข้อมูลไม่พอ

กฎเหล็กความเชื่อมโยง DFD (ห้ามวาดข้าม):
1. ❌ ห้ามลากลูกศรจาก **Entity -> Entity** โดยตรง (ต้องผ่าน Process)
2. ❌ ห้ามลากลูกศรจาก **Entity -> Data Store** โดยตรง (ต้องผ่าน Process)
3. ❌ ห้ามลากลูกศรจาก **Data Store -> Data Store** โดยตรง (ต้องผ่าน Process)

รวมสูตรและคีย์เวิร์ดสำคัญที่ต้องมองผ่านตาก่อนปิดมือถือวางบนเวที

CSC362 (ฐานข้อมูล)

• 1NF: กำจัด Repeating Groups, ค่าในช่องต้องเป็น Atomic, หา Composite PK
• 2NF: กำจัด Partial Dependency (ฟิลด์ธรรมดาขึ้นกับ PK บางส่วน) -> แตกตาราง
• 3NF: กำจัด Transitive Dependency (ฟิลด์ธรรมดาขึ้นกับฟิลด์ธรรมดา A -> B -> C) -> แตกตาราง
• 1:M Mapping: เอา PK ฝั่ง 1 ไปใส่เป็น FK ฝั่ง M
• M:N Mapping: แตกตาราง Bridge ตรงกลาง ดึง PK ทั้งสองฝั่งเป็น Composite PK
• Entity Integrity: PK ห้ามเป็น NULL และห้ามซ้ำ
• Referential Integrity: FK ต้องตรงกับ PK แม่ที่มีอยู่จริง หรือเป็น NULL

CSC481 (วิเคราะห์ระบบ)

• SDLC: Planning -> Analysis -> Design -> Implementation -> Maintenance
• Forward Pass: ES + Dur = EF (หลายทางเข้า เลือกค่ามากสุด)
• Backward Pass: LF - Dur = LS (หลายทางออก เลือกค่าน้อยสุด)
• Critical Path: เส้นทางที่ยาวที่สุด และ Slack = 0 ทุกตัว (ห้ามดีเลย์)
• DFD กฎเหล็ก: ห้าม Black Hole (มีแต่เข้า), ห้าม Miracle (มีแต่ออก), ห้ามลาก Entity ชน Entity ตรงๆ
