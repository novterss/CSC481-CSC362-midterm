Normalization Masterclass (UNF -> 1NF -> 2NF -> 3NF)

คู่มือฉบับสมบูรณ์: ปูพื้นฐานจากความเข้าใจ -> ดูตารางตัวอย่างจริง -> วิธีเขียนตอบในห้องสอบให้ได้ 15 คะแนนเต็ม

Step 0
UNF (Unnormalized)
ตารางรวม มีข้อมูลซ้ำซ้อน/ช่องว่าง
Step 1
1NF (First Normal)
กำจัด Repeating Group + หา Composite PK
Step 2
2NF (Second Normal)
กำจัด Partial Dependency (แตกตาราง)
Step 3
3NF (Third Normal)

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • ทำไมต้องทำ Normalization?

Normalization คืออะไร และถ้าไม่ทำจะเกิด "3 โรคร้าย (Anomalies)" อะไรบ้าง?

Normalization คือกระบวนการ "จัดระเบียบและแตกตาราง" ในฐานข้อมูลเชิงสัมพันธ์ เพื่อลดความซ้ำซ้อนของข้อมูล และป้องกันข้อผิดพลาดในการจัดการข้อมูล หากเราเก็บทุกอย่างไว้ในตารางยักษ์ตารางเดียว จะเกิดปัญหาใหญ่ 3 อย่าง เรียกว่า Anomalies:

1. Insertion Anomaly (ปัญหาตอนเพิ่มข้อมูล)

ไม่สามารถเพิ่มข้อมูลอย่างหนึ่งได้ ถ้ายังไม่มีข้อมูลอีกอย่างหนึ่ง เช่น "จะเพิ่มข้อมูลสินค้าชิ้นใหม่เข้าระบบไม่ได้ ถ้ายังไม่มีลูกค้าสั่งซื้อสินค้านั้น" เพราะไม่มี OrderID มาเป็นคีย์หลัก!

2. Deletion Anomaly (ปัญหาตอนลบข้อมูล)

การลบข้อมูลแถวหนึ่งทิ้ง กลับทำให้ข้อมูลสำคัญอื่นสูญหายไปด้วย เช่น "ลูกค้าขอยกเลิกคำสั่งซื้อ เราลบแถวบิลนั้นทิ้ง ข้อมูลชื่อและที่อยู่ของลูกค้าก็พลอยหายสาบสูญไปจากฐานข้อมูลด้วย!"

3. Update Anomaly (ปัญหาตอนแก้ไขข้อมูล)

เมื่อข้อมูลซ้ำซ้อนกันหลายแถว เช่น ลูกค้าคนเดิมซื้อ 10 ครั้ง มีที่อยู่ซ้ำ 10 แถว พอเขาย้ายบ้าน ถ้าแก้ไม่ครบทุกแถว ข้อมูลจะ "ขัดแย้งกันเอง (Inconsistent Data)"

ขั้นที่ 1 การแปลงเป็น 1NF (First Normal Form)

หัวใจของ 1NF:
1. เติมข้อมูลลงในทุกช่องว่างให้ครบ เพื่อให้ทุกช่องเป็น Atomic Value (ค่าเดี่ยว ไม่ซ้อนกัน)
2. กำหนด Primary Key: ในเมื่อ 1 บิลมีสินค้าได้หลายชิ้น คีย์เดียวระบุแถวไม่ได้ จึงต้องใช้ Composite Primary Key คู่กัน คือ (OrderID, ProductID)

⚠️ ทำไม 1NF ยังไม่พอ? สังเกตแถวที่ 1 กับ 2: บิล 1001 มีชื่อนาย สมชาย ซ้ำกัน 2 แถว! ถ้าสมชายย้ายบ้านเราต้องตามแก้ที่อยู่ทั้ง 2 แถว เพราะเกิดปัญหา Partial Dependency

ขั้นที่ 2 การแปลงเป็น 2NF (Second Normal Form)

หัวใจของ 2NF: กำจัด Partial Dependency (ความขึ้นตรงต่อคีย์หลักเพียงบางส่วน)
คีย์หลักเรามี 2 ตัวคือ (OrderID, ProductID) เราต้องตรวจว่ามีฟิลด์ไหนแอบไปขึ้นกับตัวใดตัวหนึ่งหรือไม่:
  • • OrderID, ProductID -> Quantity (จำนวนสินค้าที่ซื้อ ขึ้นอยู่กับทั้งเลขที่บิลและรหัสสินค้า -> Full Dependency ผ่าน!)
  • • OrderID -> OrderDate, CustomerID, CustomerName, CustomerAddress (ขึ้นกับ OrderID ตัวเดียว ไม่เกี่ยวกับสินค้าเลย -> เกิด Partial!)
  • • ProductID -> ProductName, UnitPrice (ขึ้นกับ ProductID ตัวเดียว ไม่เกี่ยวกับบิลเลย -> เกิด Partial!)
วิธีแก้ 2NF: แตกออกเป็น 3 ตารางเพื่อแยกฟิลด์ที่ขึ้นกับคีย์บางส่วนออกไป!

⚠️ ทำไม 2NF ยังไม่พอ? ดูที่ตาราง ORDER: ฟิลด์ CustomerName มันไม่ได้ขึ้นตรงกับ OrderID แต่ขึ้นกับ CustomerID ที่ไม่ใช่คีย์หลัก! เกิดเป็น Transitive Dependency

ขั้นที่ 3 การแปลงเป็น 3NF (Third Normal Form - สมบูรณ์แบบ!)

หัวใจของ 3NF: กำจัด Transitive Dependency (A -> B -> C)
ในตาราง ORDER มีความสัมพันธ์แบบลูกโซ่: OrderID -> CustomerID -> CustomerName, CustomerAddress
*CustomerName พึ่งพา CustomerID ซึ่ง CustomerID เป็นแค่ฟิลด์ธรรมดา ไม่ใช่ Primary Key ของตาราง Order!*
วิธีแก้ 3NF: ตัด CustomerID และข้อมูลลูกค้าทั้งหมดแยกออกไปสร้างเป็นตาราง CUSTOMER ต่างหาก!

✍️ ส่วนที่ 3: วิธีเขียนตอบในกระดาษข้อสอบจริง (Exam Blueprint)

สูตรเขียนตอบ 4 ขั้นตอน ให้ได้ 15 คะแนนเต็ม:

เวลาอาจารย์ตรวจข้อสอบ อาจารย์จะมองหา: 1. ชื่อตาราง 2. การขีดเส้นใต้ Primary Key 3. การใส่ดอกจัน Foreign Key และ 4. การกระจายฟิลด์ที่ถูกต้อง ให้เขียนตอบตามแพทเทิร์นนี้เป๊ะๆ ครับ:

// บรรทัดที่ 1: ตอบ 1NF 1NF: ORDER_1NF (OrderID, OrderDate, CustomerID, CustomerName, CustomerAddress, ProductID, ProductName, UnitPrice, Quantity) *เหตุผล: กำจัด Repeating Groups ให้เป็น Atomic Value และกำหนด Composite PK (OrderID, ProductID) // บรรทัดที่ 2: ตอบ 2NF 2NF: 1. ORDER (OrderID, OrderDate, CustomerID, CustomerName, CustomerAddress) 2. PRODUCT (ProductID, ProductName, UnitPrice) 3. CUSTOMER (CustomerID, CustomerName, CustomerAddress) 2. ORDER (OrderID, OrderDate, CustomerID*) 3. PRODUCT (ProductID, ProductName, UnitPrice) 4. ⚠️ ส่วนที่ 4: กับดักข้อสอบ & จุดที่นักศึกษาชอบทำผิด (ระวังเสียคะแนนฟรี)

❌ จุดผิดที่ 1: ลืมขีดเส้นใต้ Primary Key — ข้อสอบออกแบบฐานข้อมูล ถ้าไม่ขีดเส้นใต้ PK อาจารย์จะหักคะแนนทันทีครึ่งหนึ่ง!

❌ จุดผิดที่ 2: ใน 3NF ลืมทิ้ง Foreign Key ไว้เชื่อมโยง — ตอนแยกตาราง CUSTOMER ออกมา เด็กหลายคนลืมใส่ CustomerID* ไว้ในตาราง ORDER ทำให้ตารางหลุดลอย เชื่อมหากันไม่ได้

❌ จุดผิดที่ 3: ในตาราง ORDER_DETAIL ลืมทำ Composite PK — ตารางรายการสั่งซื้อ ต้องขีดเส้นใต้ทั้ง OrderID และ ProductID ร่วมกันเป็น PK เสมอ

คู่มือการออกแบบ ER Diagram (Chen & Crow's Foot)

คู่มือฉบับสมบูรณ์: แกะโจทย์ภาษาไทย/อังกฤษ -> สัญลักษณ์ทุกชนิด -> ตัวอย่างเคสคลินิกจริง -> เช็กลิสต์ส่งงาน

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • วิธีแกะโจทย์ข้อสอบเป็น ERD

กฎ 3 ข้อในการเปลี่ยนโจทย์บรรยายเป็นภาพไดอะแกรม:

เวลาอ่านโจทย์ข้อสอบยาว 1 หน้ากระดาษ อย่าเพิ่งตกใจ ให้หยิบปากกาไฮไลต์มาคัดแยกคำตามกฎนี้ทันที:

1. คำนามหลัก = Entity (สี่เหลี่ยม)

คือสิ่งที่มีตัวตนในระบบ เช่น ลูกค้า (CUSTOMER), สินค้า (PRODUCT), อาจารย์ (INSTRUCTOR), วิชา (COURSE)

2. คำกริยา = Relationship (ข้าวหลามตัด)

คือความสัมพันธ์ระหว่างเอนทิตี เช่น ลูกค้า "สั่งซื้อ (ORDERS)" สินค้า, อาจารย์ "สอน (TEACHES)" วิชา

3. รายละเอียด = Attribute (วงรี)

คือคุณสมบัติที่ติดตัวเอนทิตี เช่น รหัส (ID), ชื่อ (Name), ที่อยู่ (Address), ราคา (Price), เงินเดือน (Salary)

📖 สัญลักษณ์ Attribute ทุกชนิดที่ออกสอบ
ชนิดของ Attributeสัญลักษณ์ (Chen)ตัวอย่างในชีวิตจริง
1. Simple / Atomic วงรีเส้นเดี่ยวธรรมดา เงินเดือน (Salary), เพศ (Gender)
2. Composite Attribute วงรีที่แตกกิ่งย่อยออกมา ชื่อ-สกุล Name (แตกเป็น First, Last)
3. Multi-valued Attribute วงรี 2 ชั้น (Double Oval) เบอร์โทรศัพท์ (มีหลายเบอร์), ทักษะ (Skills)
4. Derived Attribute วงรีเส้นประ (Dashed Oval) อายุ Age (คำนวณจาก วันเกิด DateOfBirth)
5. Primary Key วงรี + ขีดเส้นใต้ข้อความ รหัสประจำตัว เช่น CustomerID, EmpID
📖 ความต่าง: Strong vs Weak Entity
🟦 Strong Entity (เอนทิตีปกติ):
เป็นเอกเทศ อยู่ได้ด้วยตัวเอง มี Primary Key ของตัวเองชัดเจน เช่น EMPLOYEE (รหัสพนักงาน EmpID)
*สัญลักษณ์: สี่เหลี่ยมผืนผ้าเส้นเดี่ยว
🟪 Weak Entity (เอนทิตีอ่อนแอ):
อยู่ตามลำพังไม่ได้ ต้องพึ่งพาการมีอยู่ของ Strong Entity (Existence Dependent) และไม่มี PK สมบูรณ์ในตัวเอง เช่น DEPENDENT (บุตรของพนักงาน — ถ้าพนักงานลาออก ข้อมูลบุตรก็ต้องถูกลบทิ้งตาม)
*สัญลักษณ์: สี่เหลี่ยมเส้นคู่ (Double Rectangle) และความสัมพันธ์ก็เป็นรูปข้าวหลามตัดเส้นคู่

1. Superkey

คือฟิลด์ใดๆ หรือกลุ่มฟิลด์ใดๆ ที่ระบุแต่ละแถวได้ไม่ซ้ำกัน เช่น: (StudentID), (CitizenID), (StudentID, FullName), (CitizenID, GPA)
*หมายเหตุ: จะมีฟิลด์แถมติดมาด้วยก็ได้ ขอแค่ห้ามซ้ำกัน

2. Candidate Key (คีย์คู่แข่ง)

คือ Superkey ขั้นต่ำสุด (Minimal Superkey) ที่ไม่มีฟิลด์ส่วนเกินติดมา ในตารางนี้มี 3 ตัว: StudentID, CitizenID, Email (ทั้ง 3 ตัวนี้ต่างมีสิทธิ์ได้รับเลือกเป็น Primary Key)

3. Primary Key (PK - คีย์หลัก)

คือ Candidate Key ที่ผู้ออกแบบระบบเลือกขึ้นมาเป็นตัวแทนระบุแถวอย่างเป็นทางการ ในที่นี้เราเลือก StudentID (ส่วน CitizenID และ Email ที่ไม่ถูกเลือกจะเรียกว่า Alternate Key)

4. Foreign Key (FK - คีย์นอก)

คือฟิลด์ที่นำไปวางไว้ในอีกตารางหนึ่ง เพื่อใช้เป็นตัวเชื่อมโยงชี้กลับมายัง Primary Key ของตารางนี้ เพื่อสร้างความสัมพันธ์เชิงโครงสร้างข้อมูล

🛡️ ส่วนที่ 2: กฎความถูกต้อง 2 ข้อ (Relational Integrity Constraints)

1. Entity Integrity (ความถูกต้องแห่งเอนทิตี)

🌊 Waterfall Model (แบบดั้งเดิม)

W

• ลักษณะ: ทำงานเป็นขั้นบันไดทีละขั้น เฟสก่อนหน้าต้องเสร็จ 100% ถึงจะเริ่มเฟสถัดไปได้
• ข้อดี: วางแผนชัดเจน ควบคุมเอกสารและงบประมาณได้ง่าย เหมาะกับโปรเจกต์ที่ Requirement นิ่ง ไม่เปลี่ยน
• ข้อเสีย: ไม่ยืดหยุ่น ถ้าลูกค้าเปลี่ยน Requirement กลางคันจะแก้ยากมาก และเห็นระบบตอนปลายสุดเท่านั้น

⚡ Agile Methodologies (แบบสมัยใหม่)

A

• ลักษณะ: แบ่งการทำงานเป็นรอบสั้นๆ เรียกว่า Sprint (1-4 สัปดาห์) มีการส่งมอบชิ้นงานที่ใช้งานได้จริงในทุกรอบ
• ข้อดี: ยืดหยุ่นสูง รับมือกับการเปลี่ยนแปลงได้ดี ลูกค้าเห็นงานตลอดเวลา
• ข้อเสีย: ควบคุม Scope และงบประมาณสุดท้ายได้ยาก หากไม่มีวินัยอาจเกิด Scope Creep ได้ง่าย

Feasibility 4 ด้าน & SWOT/TOWS Matrix

การศึกษาความเป็นไปได้และการจับคู่กลยุทธ์ตามสไลด์เคสศึกษา 7-Eleven

🔍 Feasibility Study (ความเป็นไปได้ 4 ด้าน)

4
  • • 1. Economic Feasibility: ความคุ้มค่าทางการเงิน (Cost-Benefit Analysis, TCO, ROI, Payback Period)
  • • 2. Technical Feasibility: เทคโนโลยีและฮาร์ดแวร์/ทีมงานมีความพร้อมรองรับได้หรือไม่
  • • 3. Operational Feasibility: ระบบใหม่เข้ากับการทำงานของคนในองค์กรและแก้ปัญหาได้จริงไหม
  • • 4. Schedule Feasibility: สามารถพัฒนาระบบให้เสร็จทันเวลาที่กำหนดได้หรือไม่

🎯 TOWS Matrix (การจับคู่กลยุทธ์)

T
กลยุทธ์เชิงรุก (S + O): ใช้จุดแข็ง วิ่งเข้าหาโอกาสที่เปิดอยู่เพื่อเติบโตก้าวกระโดด
กลยุทธ์เชิงแก้ไข (W + O): พยายามปิดจุดอ่อนภายใน เพื่อไม่ให้เสียโอกาสสำคัญภายนอกไป
กลยุทธ์เชิงป้องกัน (S + T): ใช้จุดแข็งเป็นเกราะป้องกันภัยคุกคามจากภายนอก
กลยุทธ์เชิงรับ (W + T): ลดความเสี่ยงที่เลวร้ายที่สุด (จุดที่จุดอ่อนตรงกับภัยคุกคามพอดี)

📖 ส่วนที่ 1: หัวใจของสายงานวิกฤต (ทำไมต้องหา?)

Critical Path คืออะไร?

• สายงานวิกฤต (Critical Path): คือลำดับงานที่ยาวที่สุดตั้งแต่เริ่มจนจบโครงการ ซึ่งเป็นตัวกำหนด "ระยะเวลาที่สั้นที่สุดที่โครงการจะสร้างเสร็จได้จริง"

• กฎเหล็ก: งานทุกงานที่อยู่บนสายนี้จะมี Slack (เวลาลอยตัว) = 0 หมายความว่า "ห้ามงานบนสายนี้ล่าช้าแม้แต่วันเดียว เพราะจะทำให้โปรเจกต์ดีเลย์ทันที!"

📦 โครงสร้างกล่อง Node 6 ช่อง (Activity On Node)

ในห้องสอบ อาจารย์มักจะให้วาดกล่องสี่เหลี่ยมแบ่งเป็น 6 ช่องเพื่อกรอกตัวเลขดังนี้:

ES (เริ่มเร็วสุด) Duration (ระยะเวลา) EF (เสร็จเร็วสุด)
LS (เริ่มช้าสุด) Slack (เวลาลอยตัว) LF (เสร็จช้าสุด)
✍️ ส่วนที่ 2: วิธีทดเลขในกระดาษข้อสอบทีละก้าว (Step-by-Step Walkthrough)

วิธีคำนวณจริงจากแบบฝึกหัดที่ 1 (Activity A -> H):

➡️ ขั้นที่ 1: Forward Pass (เดินหน้าจากซ้ายไปขวา)

สูตร: ES + Duration = EF
1. งานแรกสุด (A): เริ่มที่ ES = 0 -> EF = 0 + 3 = 3
2. งาน B (ต่อจาก A): ES = 3 -> EF = 3 + 4 = 7
3. งาน C (ต่อจาก A): ES = 3 -> EF = 3 + 6 = 9
4. งาน D (ต่อจาก B): ES = 7 -> EF = 7 + 6 = 13
5. งาน E (ต่อจาก B): ES = 7 -> EF = 7 + 4 = 11
6. งาน F (ต่อจาก C): ES = 9 -> EF = 9 + 4 = 13
7. งาน G (ต่อจาก D): ES = 13 -> EF = 13 + 6 = 19
8. 🔥 จุดระวังงาน H (มี E และ F ส่งมาทั้งคู่):
    E มี EF = 11, F มี EF = 13
    👉 กฎเหล็ก: เลือกค่ามากที่สุด (MAX) เสมอ!
    ดังนั้น ES ของ H = 13 -> EF = 13 + 8 = 21 วัน (เวลารวมทั้งโครงการ)

⬅️ ขั้นที่ 2: Backward Pass (ถอยหลังจากขวาไปซ้าย)

สูตร: LF - Duration = LS
1. งานสุดท้าย (H และ G): ให้ LF = 21 (เวลารวมโครงการ)
    • งาน H: LF = 21 -> LS = 21 - 8 = 13
    • งาน G: LF = 21 -> LS = 21 - 6 = 15
2. งาน F (ส่งให้ H): LF = 13 -> LS = 13 - 4 = 9
3. งาน E (ส่งให้ H): LF = 13 -> LS = 13 - 4 = 9
4. งาน D (ส่งให้ G): LF = 15 -> LS = 15 - 6 = 9
5. งาน C (ส่งให้ F): LF = 9 -> LS = 9 - 6 = 3
6. 🔥 จุดระวังงาน B (ส่งให้ D และ E):
    D มี LS = 9, E มี LS = 9 -> LF ของ B = 9 -> LS = 9 - 4 = 5
7. 🔥 จุดระวังงาน A (ส่งให้ B และ C):
    B มี LS = 5, C มี LS = 3
    👉 กฎเหล็ก: เลือกค่าน้อยที่สุด (MIN) เสมอ!
    ดังนั้น LF ของ A = 3 -> LS = 3 - 3 = 0

Data Flow Diagram (DFD) & กฎเหล็ก 3 ข้อ

การจำลองการไหลของข้อมูล: Context Diagram ต่างจาก Diagram 0 อย่างไร -> 3 ข้อผิดพลาดร้ายแรง -> กฎห้ามลากเส้นข้าม

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • Context Diagram ต่างจาก Diagram 0 อย่างไร?
1. Context Diagram (Level 0 DFD)

• คือ "ภาพมุมมองสูงสุดของระบบ (Bird's Eye View)"
• มี Process เพียงวงกลมเดียวตรงกลาง (Process 0) แทนทั้งระบบ เช่น "Food Ordering System"
• รอบๆ มีเฉพาะ External Entity (เช่น ลูกค้า, ครัว, ธนาคาร) ส่งข้อมูลเข้า/ออก
• ⚠️ กฎเหล็ก: ห้ามมี Data Store (คลังข้อมูล) โผล่มาใน Context Diagram เด็ดขาด!

2. Diagram 0 (Level 1 DFD)

• คือการ "ระเบิดขยายรายละเอียดข้างใน Process 0 ออกมา (Explosion)"
• แตกเป็น Process ย่อยๆ ที่มีเลขกำกับ เช่น 1.0 รับออเดอร์, 2.0 คิดเงิน, 3.0 ตัดสต็อก
• ✔️ มี Data Store (D1, D2 เช่น แฟ้มข้อมูลสินค้า, แฟ้มคำสั่งซื้อ) ปรากฏได้ในระดับนี้

📊 ส่วนที่ 2: ตัวอย่าง Context Diagram สมบูรณ์แบบ (ระบบสั่งอาหาร)

ผังแสดงการไหลของข้อมูล (Inputs & Outputs):

⚠️ ส่วนที่ 3: กฎเหล็ก 3 ข้อผิดพลาดร้ายแรง (DFD Errors) ที่ห้ามวาด

3 ข้อผิดพลาดที่อาจารย์หักคะแนนหนักที่สุด:

🕳️ 1. Black Hole (หลุมดำ)

อาการ: Process มีแต่ลูกศรไหลเข้า (Inputs) แต่ไม่มีลูกศรไหลออก (Outputs) เลยแม้แต่เส้นเดียว!

เหมือนทิ้งข้อมูลลงหลุมดำ ระบบประมวลผลแล้วไม่ได้ส่งอะไรให้ใครเลย ถือว่าผิดหลักการทำงานของระบบสารสนเทศ

✨ 2. Miracle (ปาฏิหาริย์)

อาการ: Process มีแต่ลูกศรส่งออก (Outputs) แต่ไม่มีข้อมูลไหลเข้า (Inputs) เลย!

จู่ๆ ระบบก็เสกข้อมูลส่งออกไปเองได้โดยไม่รับข้อมูลต้นทางเข้ามา ถือเป็นปาฏิหาริย์ที่ผิดหลักการ

🌫️ 3. Gray Hole (หลุมเทา)

อาการ: ข้อมูลขาเข้าไม่เพียงพอที่จะสร้างข้อมูลขาออกได้

เช่น รับเข้ามาแค่ "รหัสพนักงาน" แต่ขาส่งออกกลับสร้าง "รายงานยอดขายประจำปี" ซึ่งข้อมูลขาเข้าไม่สมเหตุสมผล

กฎเหล็กการลากเส้นเชื่อมโยง (ห้ามลากข้ามเด็ดขาด):
1. ❌ ห้ามลาก Entity -> Entity โดยตรง (ต้องส่งผ่าน Process เสมอ)
2. ❌ ห้ามลาก Entity -> Data Store โดยตรง (ลูกค้าเดินไปเปิดแฟ้มข้อมูลเองไม่ได้ ต้องผ่าน Process)
3. ❌ ห้ามลาก Data Store -> Data Store โดยตรง (แฟ้มข้อมูลคุยกันเองไม่ได้ ต้องมี Process มาดึงข้อมูล)

CSC362 (ฐานข้อมูล)

• 1NF: กำจัด Repeating Groups, ค่าในช่องต้องเป็น Atomic, หา Composite PK
• 2NF: กำจัด Partial Dependency (ฟิลด์ธรรมดาขึ้นกับ PK บางส่วน) -> แตกตาราง
• 3NF: กำจัด Transitive Dependency (ฟิลด์ธรรมดาขึ้นกับฟิลด์ธรรมดา A -> B -> C) -> แตกตาราง
• 1:M Mapping: เอา PK ฝั่ง 1 ไปใส่เป็น FK ฝั่ง M
• M:N Mapping: แตกตาราง Bridge ตรงกลาง ดึง PK ทั้งสองฝั่งเป็น Composite PK
• Entity Integrity: PK ห้ามเป็น NULL และห้ามซ้ำ
• Referential Integrity: FK ต้องตรงกับ PK แม่ที่มีอยู่จริง หรือเป็น NULL

CSC481 (วิเคราะห์ระบบ)

• SDLC: Planning -> Analysis -> Design -> Implementation -> Maintenance
• Forward Pass: ES + Dur = EF (หลายทางเข้า เลือกค่ามากสุด)
• Backward Pass: LF - Dur = LS (หลายทางออก เลือกค่าน้อยสุด)
• Critical Path: เส้นทางที่ยาวที่สุด และ Slack = 0 ทุกตัว (ห้ามดีเลย์)
• DFD กฎเหล็ก: ห้าม Black Hole (มีแต่เข้า), ห้าม Miracle (มีแต่ออก), ห้ามลาก Entity ชน Entity ตรงๆ
