📖 ส่วนที่ 1: อ่านทำความเข้าใจ • ทำไมต้องทำ Normalization?

Normalization คืออะไร และถ้าไม่ทำจะเกิด "3 โรคร้าย (Anomalies)" อะไรบ้าง?

Normalization คือกระบวนการ "จัดระเบียบและแตกตาราง" ในฐานข้อมูลเชิงสัมพันธ์ เพื่อลดความซ้ำซ้อนของข้อมูล และป้องกันข้อผิดพลาดในการจัดการข้อมูล หากเราเก็บทุกอย่างไว้ในตารางยักษ์ตารางเดียว จะเกิดปัญหาใหญ่ 3 อย่าง เรียกว่า Anomalies:

1. Insertion Anomaly (ปัญหาตอนเพิ่มข้อมูล)

ไม่สามารถเพิ่มข้อมูลอย่างหนึ่งได้ ถ้ายังไม่มีข้อมูลอีกอย่างหนึ่ง เช่น "จะเพิ่มข้อมูลสินค้าชิ้นใหม่เข้าระบบไม่ได้ ถ้ายังไม่มีลูกค้าสั่งซื้อสินค้านั้น" เพราะไม่มี OrderID มาเป็นคีย์หลัก!

2. Deletion Anomaly (ปัญหาตอนลบข้อมูล)

การลบข้อมูลแถวหนึ่งทิ้ง กลับทำให้ข้อมูลสำคัญอื่นสูญหายไปด้วย เช่น "ลูกค้าขอยกเลิกคำสั่งซื้อ เราลบแถวบิลนั้นทิ้ง ข้อมูลชื่อและที่อยู่ของลูกค้าก็พลอยหายสาบสูญไปจากฐานข้อมูลด้วย!"

3. Update Anomaly (ปัญหาตอนแก้ไขข้อมูล)

เมื่อข้อมูลซ้ำซ้อนกันหลายแถว เช่น ลูกค้าคนเดิมซื้อ 10 ครั้ง มีที่อยู่ซ้ำ 10 แถว พอเขาย้ายบ้าน ถ้าแก้ไม่ครบทุกแถว ข้อมูลจะ "ขัดแย้งกันเอง (Inconsistent Data)"

ขั้นที่ 2 การแปลงเป็น 2NF (Second Normal Form)

หัวใจของ 2NF: กำจัด Partial Dependency (ความขึ้นตรงต่อคีย์หลักเพียงบางส่วน)
คีย์หลักเรามี 2 ตัวคือ (OrderID, ProductID) เราต้องตรวจว่ามีฟิลด์ไหนแอบไปขึ้นกับตัวใดตัวหนึ่งหรือไม่:
  • • OrderID, ProductID -> Quantity (จำนวนสินค้าที่ซื้อ ขึ้นอยู่กับทั้งเลขที่บิลและรหัสสินค้า -> Full Dependency ผ่าน!)
  • • OrderID -> OrderDate, CustomerID, CustomerName, CustomerAddress (ขึ้นกับ OrderID ตัวเดียว ไม่เกี่ยวกับสินค้าเลย -> เกิด Partial!)
  • • ProductID -> ProductName, UnitPrice (ขึ้นกับ ProductID ตัวเดียว ไม่เกี่ยวกับบิลเลย -> เกิด Partial!)

คู่มือการออกแบบ ER Diagram (Chen & Crow's Foot)

คู่มือฉบับสมบูรณ์: แกะโจทย์ภาษาไทย/อังกฤษ -> สัญลักษณ์ทุกชนิด -> ตัวอย่างเคสคลินิกจริง -> กระดาษคำตอบห้องสอบ

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • กฎ 3 ข้อในการแกะโจทย์ข้อสอบเป็น ERD

วิธีคัดแยกคำจากโจทย์ให้ออกมาเป็นโครงร่างไดอะแกรม:

เวลาอ่านโจทย์ข้อสอบยาว 1 หน้ากระดาษ ให้หยิบปากกาไฮไลต์มาคัดแยกคำตามกฎ 3 ข้อนี้ทันที:

1. คำนามหลัก = Entity (สี่เหลี่ยม)

คือสิ่งที่มีตัวตนในระบบ เช่น ลูกค้า (CUSTOMER), สินค้า (PRODUCT), แพทย์ (DOCTOR), คนไข้ (PATIENT)

2. คำกริยา = Relationship (ข้าวหลามตัด)

คือความสัมพันธ์ระหว่างเอนทิตี เช่น แพทย์ "ตรวจรักษา (TREATS)" คนไข้, ลูกค้า "สั่งซื้อ (ORDERS)" สินค้า

3. คำขยายย่อย = Attribute (วงรี)

คือคุณสมบัติที่ติดตัวเอนทิตี เช่น รหัส (ID), ชื่อ (Name), ที่อยู่ (Address), วันเกิด (DOB), เบอร์โทร (Phone)

📖 สัญลักษณ์ Attribute ทุกชนิดที่ออกสอบ
ชนิดของ Attributeสัญลักษณ์ (Chen)ตัวอย่างในชีวิตจริง
1. Simple / Atomic วงรีเส้นเดี่ยวธรรมดา เงินเดือน (Salary), เพศ (Gender)
2. Composite Attribute วงรีที่แตกกิ่งย่อยออกมา ชื่อ-สกุล Name (แตกเป็น Fname, Lname)
3. Multi-valued Attribute วงรี 2 ชั้น (Double Oval) เบอร์โทรศัพท์ (มีได้หลายเบอร์), ทักษะ (Skills)
4. Derived Attribute วงรีเส้นประ (Dashed Oval) อายุ Age (คำนวณจาก วันเกิด DateOfBirth)
5. Primary Key วงรี + ขีดเส้นใต้ข้อความ รหัสประจำตัว เช่น PatientID, DoctorID
📖 ความต่าง: Strong vs Weak Entity
🟦 Strong Entity (เอนทิตีปกติ):
เป็นเอกเทศ อยู่ได้ด้วยตัวเอง มี Primary Key ของตัวเองชัดเจน เช่น DOCTOR (รหัสแพทย์ DoctorID)
*สัญลักษณ์: สี่เหลี่ยมผืนผ้าเส้นเดี่ยว
🟪 Weak Entity (เอนทิตีอ่อนแอ):
อยู่ตามลำพังไม่ได้ ต้องพึ่งพาการมีอยู่ของ Strong Entity (Existence Dependent) และไม่มี PK สมบูรณ์ในตัวเอง เช่น DEPENDENT (ผู้ติดต่อฉุกเฉินของคนไข้ — ถ้าคนไข้ลบประวัติ ข้อมูลผู้ติดต่อก็ต้องถูกลบทิ้งตาม)
*สัญลักษณ์: สี่เหลี่ยมเส้นคู่ (Double Rectangle) และความสัมพันธ์ก็เป็นรูปข้าวหลามตัดเส้นคู่

คือฟิลด์ใดๆ หรือกลุ่มฟิลด์ใดๆ ที่ระบุแต่ละแถวได้ไม่ซ้ำกัน เช่น: (StudentID), (CitizenID), (StudentID, FullName), (CitizenID, GPA)
*หมายเหตุ: จะมีฟิลด์แถมติดมาด้วยก็ได้ ขอแค่ห้ามซ้ำกัน

2. Candidate Key (คีย์คู่แข่ง)

คือ Superkey ขั้นต่ำสุด (Minimal Superkey) ที่ไม่มีฟิลด์ส่วนเกินติดมา ในตารางนี้มี 3 ตัว: StudentID, CitizenID, Email (ทั้ง 3 ตัวนี้ต่างมีสิทธิ์ได้รับเลือกเป็น Primary Key)

3. Primary Key (PK - คีย์หลัก)

คือ Candidate Key ที่ผู้ออกแบบระบบเลือกขึ้นมาเป็นตัวแทนระบุแถวอย่างเป็นทางการ ในที่นี้เราเลือก StudentID (ส่วน CitizenID และ Email ที่ไม่ถูกเลือกจะเรียกว่า Alternate Key)

4. Foreign Key (FK - คีย์นอก)

คือฟิลด์ที่นำไปวางไว้ในอีกตารางหนึ่ง เพื่อใช้เป็นตัวเชื่อมโยงชี้กลับมายัง Primary Key ของตารางนี้ เพื่อสร้างความสัมพันธ์เชิงโครงสร้างข้อมูล

แนวข้อสอบ: "จงอธิบายความหมายและความสำคัญของ Entity Integrity และ Referential Integrity"

1. Entity Integrity:
• ความหมาย: เป็นกฎที่ระบุว่าในทุกแถว (Tuple) ของความสัมพันธ์ จะต้องมี Primary Key ที่มีค่าระบุตัวตนได้ชัดเจน โดยค่าของ Primary Key จะต้อง ห้ามเป็นค่าว่าง (NOT NULL) และ ห้ามมีค่าซ้ำกัน (UNIQUE)
• ความสำคัญ: เพื่อรับประกันว่าระบบจะสามารถระบุและค้นหาแต่ละเรคคอร์ดในตารางได้อย่างถูกต้องแม่นยำ 100% โดยไม่เกิดความสับสนหรือข้อมูลชนกัน

2. Referential Integrity:
• ความหมาย: เป็นกฎที่ควบคุมความสอดคล้องระหว่าง 2 ตาราง โดยระบุว่าค่าของ Foreign Key ในตารางลูก จะต้อง มีค่าตรงกับ Primary Key ในตารางแม่ที่มีอยู่จริง หรือมีค่าเป็น NULL (ในกรณีที่ยังไม่มีความสัมพันธ์)
• ความสำคัญ: ป้องกันไม่ให้เกิดปัญหา "Orphan Records (ข้อมูลกำพร้า)" เช่น มีข้อมูลพนักงานที่ชี้ไปหาแผนกที่ไม่มีตัวตนอยู่ในระบบ

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • วงจร SDLC 5 ขั้นตอน & เอกสารส่งมอบ (Deliverables)

SDLC (Systems Development Life Cycle) คือพิมพ์เขียวมาตรฐานที่นักวิเคราะห์ระบบ (SA) ใช้ควบคุมโปรเจกต์ตั้งแต่เริ่มต้นจนสิ้นสุดระบบ ทุกเฟสจะต้องมี "ผลลัพธ์หรือเอกสารส่งมอบ (Deliverables)" เพื่อส่งต่อให้เฟสถัดไป:

1. Planning (การวางแผนโครงการ)

ตอบคำถาม: "ทำไมต้องทำ? ทำแล้วคุ้มไหม?"

• กิจกรรมหลัก: รับคำขอพัฒนาระบบ (System Request), วิเคราะห์ปัญหา/โอกาส, ศึกษาความเป็นไปได้ (Feasibility Study), กำหนดขอบเขตงาน (Scope) และจัดสรรงบประมาณ/ทีมงาน
• 📦 เอกสารส่งมอบ (Deliverables): Feasibility Study Report (รายงานความเป็นไปได้) และ Project Charter / Project Plan (แผนบริหารโครงการ)

2. Analysis (การวิเคราะห์ระบบ)

ตอบคำถาม: "ระบบใหม่ต้องทำอะไรได้บ้าง (What to do)?"

• กิจกรรมหลัก: รวบรวมความต้องการ (Requirement Gathering) โดยการสัมภาษณ์/สังเกต/แจกแบบสอบถาม, วิเคราะห์ระบบปัจจุบัน (AS-IS) เพื่อหาระบบที่ควรจะเป็น (TO-BE), สร้างแบบจำลองการไหลของข้อมูล
• 📦 เอกสารส่งมอบ (Deliverables): SRS (System Requirements Specification), Data Flow Diagram (DFD Level 0 & 1), Use Case Diagram

3. Design (การออกแบบระบบ)

ตอบคำถาม: "จะสร้างระบบขึ้นมาอย่างไร (How to build)?"

• กิจกรรมหลัก: แปลง Requirement ให้เป็นแบบพิมพ์เขียวเชิงเทคนิค: ออกแบบหน้าจอ UI/UX (Wireframe/Mockup), ออกแบบฐานข้อมูล (ER Diagram & Relational Schema), ออกแบบ Architecture (Client-Server, Cloud API) และระบบรักษาความปลอดภัย
• 📦 เอกสารส่งมอบ (Deliverables): System Design Document, ERD & Data Dictionary, UI/UX Prototypes, Database Schema

4. Implementation (การนำไปใช้ / พัฒนาจริง)

ตอบคำถาม: "สร้างโค้ด ทดสอบ และเปิดระบบใช้งานจริง"

• กิจกรรมหลัก: เขียนโปรแกรม (Coding), ทดสอบระบบ 4 ระดับ (Unit Test -> Integration Test -> System Test -> UAT: User Acceptance Testing), ติดตั้งฮาร์ดแวร์/ซอฟต์แวร์, อบรมผู้ใช้งาน (User Training), แปลงระบบงานเก่าสู่ระบบใหม่ (System Conversion: Direct, Parallel, Pilot, Phased)
• 📦 เอกสารส่งมอบ (Deliverables): Installed Software (ซอฟต์แวร์ที่ใช้งานได้จริง), Test Cases & Results, User Manual (คู่มือผู้ใช้)

5. Maintenance (การบำรุงรักษา)

ตอบคำถาม: "ดูแลให้ระบบทำงานเสถียรและปรับตามอนาคต"

• กิจกรรมหลัก: ดูแลระบบรายวัน แก้ไขปัญหาที่พบ แบ่งเป็น 4 รูปแบบ: 1. Corrective (แก้บั๊ก/ข้อผิดพลาด) 2. Adaptive (ปรับตัวตามสิ่งแวดล้อมใหม่ เช่น อัปเดต OS/Database ใหม่) 3. Perfective (ปรับปรุงความเร็ว/เพิ่มฟีเจอร์ตามที่ User ร้องขอ) 4. Preventive (บำรุงรักษาเชิงป้องกันก่อนระบบพัง)
• 📦 เอกสารส่งมอบ (Deliverables): Maintenance Log, Software Patches / Updates

📖 ส่วนที่ 2: อ่านทำความเข้าใจ • ตารางเปรียบเทียบ Waterfall vs Agile 6 มิติ
มิติการเปรียบเทียบ 🌊 Waterfall Model (แบบดั้งเดิม) ⚡ Agile / Scrum (แบบสมัยใหม่)
1. รูปแบบการทำงาน ทำเป็นขั้นบันไดทีละเฟสตามลำดับ (Sequential) เฟสเดิมต้องเสร็จ 100% ถึงจะเริ่มเฟสใหม่ได้ แบ่งเป็นรอบสั้นๆ เรียกว่า Sprint (1-4 สัปดาห์) วนลูป Plan-Build-Test ซ้ำๆ (Iterative & Incremental)
2. ความยืดหยุ่นต่อการเปลี่ยนแปลง ต่ำมาก (Rigid): ถ้าเริ่มโค้ดแล้วลูกค้าขอแก้ Requirement จะมีต้นทุนสูงมากและทำให้งานสะดุด สูงมาก (Flexible): ยินดีต้อนรับการเปลี่ยนแปลง ปรับเปลี่ยน Backlog ใน Sprint ถัดไปได้ทันที
3. การส่งมอบงาน (Delivery) ส่งมอบชิ้นงานที่ใช้ได้จริง "ตอนท้ายสุดของโครงการเพียงครั้งเดียว (Big Bang)" ส่งมอบ "Working Software ที่ใช้งานได้จริงในทุกๆ สิ้นสุด Sprint" ลูกค้าได้ลองใช้ตลอด
4. การมีส่วนร่วมของลูกค้า คุยเข้มข้นเฉพาะตอนต้นน้ำ (Requirement) แล้วเจอกันอีกทีตอนส่งมอบระบบปลายน้ำ มีส่วนร่วมตลอดเวลา (Product Owner อยู่ในทีม) มีประชุม Review ชิ้นงานทุกสัปดาห์
5. การจัดการเอกสาร เน้นเอกสารเข้มงวดมาก (Comprehensive Documentation) ทุกขั้นตอนต้องมี Sign-off อนุมัติ เน้นชิ้นงานซอฟต์แวร์ที่ใช้ได้จริงมากกว่าเอกสารหนาเตอะ (Working software over comprehensive documentation)
6. ความเหมาะสมกับโปรเจกต์ โปรเจกต์ที่ Requirement นิ่ง ชัดเจน ไม่เปลี่ยน เช่น ระบบบัญชี, ระบบการบิน, ระบบราชการ, การแพทย์ โปรเจกต์ที่ Requirement ไม่แน่นอน ตลาดเปลี่ยนไว เช่น แอป Startup, E-Commerce, เกม, AI
🔍 ส่วนที่ 3: อ่านทำความเข้าใจ • 5 เทคนิคการเก็บรวบรวมข้อมูล (Fact-Finding Techniques)

เครื่องมือสำคัญที่นักวิเคราะห์ระบบ (SA) ใช้หา Requirement ในเฟส Analysis:

ในการหาความต้องการของระบบ (Requirement Gathering) อาจารย์มักออกข้อสอบถามว่า "แต่ละเทคนิคมีจุดเด่น-จุดด้อยอย่างไร และในสถานการณ์ใดควรเลือกใช้เทคนิคใด?" สรุปเปรียบเทียบ 5 เทคนิคหลักดังนี้:

1. Interview (การสัมภาษณ์)

เจาะลึกที่สุด

• รูปแบบ: พูดคุยตัวต่อตัว (Face-to-Face) มีทั้งแบบมีโครงสร้าง (Structured) และไม่มีโครงสร้าง (Unstructured)
• ✔️ ข้อดี: ได้ข้อมูลเชิงลึก ซักถามข้อสงสัยได้ทันที สังเกตสีหน้าท่าทางได้
• ❌ ข้อเสีย: ใช้เวลาและงบประมาณสูงมาก อาจมีอคติ (Bias) จากผู้ตอบ
• 🎯 เมื่อไหร่ควรใช้: คุยกับผู้บริหารระดับสูง (CEO, ผู้จัดการฝ่าย) หรือ Key User ที่กุมนโยบายหลัก

2. Questionnaire (แบบสอบถาม)

กลุ่มคนจำนวนมาก

• รูปแบบ: แจกแบบฟอร์มกระดาษหรือ Online Form (Google Forms/MS Forms) ทั้งคำถามปลายเปิดและปลายปิด
• ✔️ ข้อดี: เก็บข้อมูลจากคนจำนวนมาก (Mass Users) ได้รวดเร็ว ประหยัด นำข้อมูลมาวิเคราะห์สถิติง่าย
• ❌ ข้อเสีย: อัตราการตอบกลับมักต่ำ (Low Response Rate) ไม่สามารถซักไซ้ข้อสงสัยได้
• 🎯 เมื่อไหร่ควรใช้: สำรวจความพึงพอใจลูกค้าทั่วไป หรือสำรวจพนักงานระดับปฏิบัติการ 500-1,000 คน

3. Observation (การสังเกตการณ์)

ดูหน้างานจริง

• รูปแบบ: นักวิเคราะห์ระบบเข้าไปนั่งดูขั้นตอนการทำงานจริงของพนักงานหน้างาน
• ✔️ ข้อดี: เห็นปัญหาจริงที่พนักงานอาจอธิบายไม่ถูก ตรวจสอบความถูกต้องจากคำพูดได้
• ❌ ข้อเสีย: Hawthorne Effect (คนทำงานเกร็งและเปลี่ยนพฤติกรรมเมื่อรู้ตัวว่าถูกเฝ้ามอง)
• 🎯 เมื่อไหร่ควรใช้: ขั้นตอนการทำงานที่ซับซ้อน เช่น การประกอบชิ้นส่วน หรือการรับออเดอร์ในครัว

4. Document Review (การตรวจเอกสาร)

ศึกษาระบบเดิม

• รูปแบบ: ตรวจสอบคู่มือการทำงานเดิม ฟอร์มกรอกข้อมูล ใบเสร็จ รายงานยอดขาย ผังองค์กร
• ✔️ ข้อดี: เข้าใจกระบวนการเดิม (AS-IS) รู้ว่าต้องใช้ฟิลด์ข้อมูลอะไรบ้าง ไม่รบกวนเวลาทำงานของคน
• ❌ ข้อเสีย: เอกสารมักล้าสมัย (Outdated) ไม่ตรงกับการปฏิบัติงานจริงในปัจจุบัน
• 🎯 เมื่อไหร่ควรใช้: ช่วงเริ่มต้นโปรเจกต์เพื่อปูพื้นฐานความเข้าใจก่อนไปสัมภาษณ์

5. JAD (Joint Application Development) • เทคนิคยอดฮิตยุคใหม่

ระดมสมองพร้อมกันทุกฝ่าย

• รูปแบบ: เวิร์กช็อปเข้มข้นที่นำทุกฝ่าย (SA, ผู้ใช้งาน, ผู้บริหาร, โปรแกรมเมอร์) มานั่งประชุมในห้องเดียวกันหลายๆ วัน โดยมี Facilitator (คนกลาง) คอยดำเนินการประชุม
• ✔️ ข้อดี: ลดความขัดแย้งข้ามแผนก ได้ข้อสรุป Requirement ที่ทุกคนเห็นพ้องต้องกัน (Consensus) ภายในระยะเวลาอันสั้น
• ❌ ข้อเสีย: มีค่าใช้จ่ายสูง และจัดตารางเวลาของทุกคนให้ว่างตรงกันได้ยากมาก
• 🎯 เมื่อไหร่ควรใช้: โครงการระบบขนาดใหญ่ที่มีความขัดแย้งระหว่างแผนกสูง และต้องการเริ่มงานอย่างเร่งด่วน

🎯 สูตรโกงคำตอบในห้องสอบ (อาจารย์ชอบถามจับคู่สถานการณ์):
• ถ้าโจทย์ระบุว่า "ผู้ใช้งานอยู่กระจายกันทั่วประเทศหลักพันคน" -> ตอบ Questionnaire (แบบสอบถาม)
• ถ้าโจทย์ระบุว่า "ต้องการทราบวิสัยทัศน์หรือนโยบายจากผู้บริหารระดับสูง" -> ตอบ Interview (การสัมภาษณ์)

ตัวอย่างโจทย์ 1: "บริษัทต้องการพัฒนาระบบเบิกจ่ายเบี้ยประกันภัยทางการแพทย์ ซึ่งมีระเบียบคปภ. กำกับชัดเจน และผิดพลาดเรื่องตัวเลขไม่ได้เลย ควรเลือกวิธีการพัฒนาระบบแบบใด?"

คำตอบที่สมบูรณ์แบบ:

2. เหตุผลประกอบ:
• พฤติกรรมผู้บริโภคและเทรนด์ร้านอาหารเปลี่ยนแปลงรวดเร็วมาก Agile รองรับการแก้ไข Requirement ได้ตลอดเวลา
• สามารถส่งมอบ MVP (Minimum Viable Product) ที่ใช้งานได้จริงออกสู่ตลาดได้ภายใน 2-4 สัปดาห์แรก เพื่อทดสอบความต้องการของผู้ใช้จริง (User Feedback)
• ลดความเสี่ยงในการลงทุนสร้างแอปนานเป็นปีแล้วเปิดตัวออกมาไม่มีใครใช้

Feasibility 5 ด้าน & SWOT / TOWS Matrix

TELOS Framework การศึกษาความเป็นไปได้ -> การแยก SWOT ภายใน vs ภายนอก -> การจับคู่กลยุทธ์ TOWS 4 มิติ (เคสศึกษา 7-Eleven)

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • การศึกษาความเป็นไปได้ 5 ด้าน (TELOS Framework)

ก่อนจะอนุมัติสร้างระบบในเฟส Planning นักวิเคราะห์ระบบต้องทำ Feasibility Study เพื่อพิสูจน์ว่าโปรเจกต์นี้ "ทำได้จริงและคุ้มค่าที่จะทำ" โดยใช้กรอบ TELOS 5 ด้าน:

1. Technical Feasibility (ด้านเทคนิค)

• มีเทคโนโลยี ฮาร์ดแวร์ ซอฟต์แวร์ และโครงข่ายสัญญาณรองรับหรือไม่?
• ทีมพัฒนามีทักษะและความเชี่ยวชาญพอไหม หรือต้องจ้าง Outsource / อบรมเพิ่ม?

2. Economic Feasibility (ด้านความคุ้มค่าทางการเงิน)

• การวิเคราะห์ต้นทุนเทียบผลประโยชน์ (Cost-Benefit Analysis)
• ROI (Return on Investment): (ผลประโยชน์สุทธิ / ต้นทุนทั้งหมด) x 100%
• Payback Period: ระยะเวลาคืนทุน (ต้องสั้นกว่าอายุการใช้งานของระบบ)
• TCO (Total Cost of Ownership): รวมค่าติดตั้ง ค่าลิขสิทธิ์ และค่าบำรุงรักษา

3. Legal & Ethical Feasibility (ด้านกฎหมายและจริยธรรม)

• ไม่ละเมิดกฎหมาย เช่น พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)
• ไม่ละเมิดลิขสิทธิ์ซอฟต์แวร์ หรือสิทธิบัตรของผู้อื่น และสอดคล้องกับข้อกำหนดภาครัฐ

4. Operational Feasibility (ด้านการปฏิบัติงาน / ผู้ใช้)

• ผู้ใช้งาน (พนักงาน) พร้อมยอมรับระบบใหม่หรือไม่? จะเกิดการต่อต้าน (User Resistance) ไหม?
• ระบบแก้ปัญหาการทำงานเดิมขององค์กรได้จริงหรือไม่ และเข้ากับวัฒนธรรมองค์กรไหม

5. Schedule Feasibility (ด้านกรอบเวลา)

• สามารถพัฒนาระบบให้เสร็จทันกำหนดการส่งมอบ (Deadlines) หรือไม่? ถ้าดีเลย์จะกระทบต่อธุรกิจอย่างไร?

📖 ส่วนที่ 2: อ่านทำความเข้าใจ • SWOT แยกปัจจัยภายใน vs ภายนอกให้เด็ดขาด

หัวใจของ SWOT คือการแยกแยะสิ่งที่ "องค์กรควบคุมได้ (ภายใน)" ออกจากสิ่งที่ "องค์กรควบคุมไม่ได้ (ภายนอก)":

🏢 ปัจจัยภายใน (Internal - องค์กรควบคุมได้เอง)

S - Strengths (จุดแข็ง):

สิ่งที่เราทำได้ดีเด่นเหนือคู่แข่ง เช่น มีสาขากระจายทั่วประเทศ, ฐานข้อมูลลูกค้าใหญ่, เงินทุนหนา, มีระบบโลจิสติกส์ของตัวเอง

W - Weaknesses (จุดอ่อน):

ข้อเสียเปรียบหรือข้อบกพร่องภายใน เช่น พนักงานหน้าสาขาขาดทักษะไอที, ระบบสต็อกเก่าทำให้อัปเดตช้า, แอปพลิเคชันยังไม่รองรับหลายภาษา

🌍 ปัจจัยภายนอก (External - สภาพแวดล้อมที่ควบคุมไม่ได้)

O - Opportunities (โอกาส):

ปัจจัยภายนอกที่เป็นประโยชน์ต่อเรา เช่น นโยบายรัฐหนุนสังคมไร้เงินสด (Cashless), พฤติกรรมผู้บริโภคนิยมสั่งของออนไลน์ส่งถึงบ้าน

T - Threats (อุปสรรค / ภัยคุกคาม):

ปัจจัยภายนอกที่อาจก่อให้เกิดความเสียหาย เช่น คู่แข่งรายใหญ่ทำสงครามตัดราคา, เงินเฟ้อทำให้กำลังซื้อลดลง, ปัญหาค่าพลังงาน/น้ำมันพุ่งสูง

การแปลง SWOT เป็นแผนกลยุทธ์ปฏิบัติการ (Action Plan):

สูตรกลยุทธ์ ความหมายและเป้าหมาย 📝 ตัวอย่างคำตอบที่ต้องเขียนในกระดาษข้อสอบ (เคส 7-Eleven)
1. กลยุทธ์ SO (เชิงรุก) ใช้จุดแข็ง (S) วิ่งเข้าหาโอกาส (O)
เพื่อสร้างการเติบโตอย่างก้าวกระโดด		 ใช้เครือข่ายสาขาที่มีมากกว่า 14,000 แห่ง (S) ผนวกกับระบบ Delivery เพื่อรองรับพฤติกรรมสั่งของด่วนถึงบ้านของผู้บริโภคยุคใหม่ (O) กลายเป็นบริการ 7-Delivery ส่งเร็วใน 30 นาที
2. กลยุทธ์ WO (เชิงแก้ไข) พลิกจุดอ่อน (W) โดยอาศัยโอกาส (O)
ปิดจุดบกพร่องเพื่อไม่ให้เสียโอกาส		 พนักงานหน้าสาขายังขาดทักษะดิจิทัลและแอปช้า (W) อาศัยโอกาสช่วงที่ภาครัฐมีโครงการส่งเสริม Digital Literacy (O) จัดโปรแกรมอบรม Reskill พนักงาน และปรับปรุงระบบ Cloud Point of Sale
3. กลยุทธ์ ST (เชิงป้องกัน) ใช้จุดแข็ง (S) เป็นเกราะต้านภัยคุกคาม (T)
รับมือคู่แข่งหรือความเสี่ยงภายนอก		 คู่แข่งทำสงครามตัดราคา (T) นำระบบฐานข้อมูลสมาชิก All-Member และ Big Data Loyalty (S) มาทำการตลาดแบบเฉพาะบุคคล (Personalized Promotion) แจกคูปองสะสมแต้มล็อกลูกค้าไว้โดยไม่ต้องแข่งตัดราคาให้เจ็บตัว
4. กลยุทธ์ WT (เชิงรับ / ถอยตั้งหลัก) ลดจุดอ่อน (W) และหลีกเลี่ยงภัยคุกคาม (T)
เพื่อลดความเสียหายร้ายแรงที่สุด		 สินค้าบางรายการค้างสต็อกนานและมีต้นทุนดูแลสูง (W) ประกอบกับสภาพเศรษฐกิจชะลอตัวและค่าพลังงานพุ่ง (T) ทำการ ยุบเลิกสินค้าที่ขายไม่ออก และปรับลดเวลาเปิดแอร์/ตู้แช่ในสาขาที่ลูกค้าเบาบาง เพื่อควบคุมกระแสเงินสด

❌ จุดผิดยอดฮิต: เอาสิ่งแวดล้อมภายนอกไปใส่ในจุดอ่อน (W) หรือจุดแข็ง (S)
เช่น เขียนว่า "จุดอ่อนคือเศรษฐกิจแย่ หรือคู่แข่งเปิดร้านติดกัน" — ผิดมหันต์!

📊 ส่วนที่ 3: อ่านทำความเข้าใจ • แผนภูมิแกนต์ (Gantt Chart) & หมุดหมาย (Milestone)

Gantt Chart คืออะไร และทำไมถึงสำคัญใน Project Management?

แผนภูมิแกนต์ (Gantt Chart) คิดค้นโดย Henry Gantt เป็นแผนภูมิแท่งแนวนอน (Horizontal Bar Chart) มาตรฐานสากลที่ใช้ในการ "วางแผน กำหนดตารางเวลา (Scheduling) และติดตามความคืบหน้า (Progress Tracking)" ของโครงการ โดยแปลงตารางกิจกรรมให้ออกมาเป็นแท่งเวลาบนปฏิทินที่ทุกคนมองเห็นภาพชัดเจนทันที

1. แกนเวลา & แท่งกิจกรรม (Task Bars)

Timeline

• แกนนอน (X-axis): คือเวลาตามปฏิทิน (วัน, สัปดาห์ หรือเดือน)
• แกนตั้ง (Y-axis): รายชื่อกิจกรรมทั้งหมดที่ต้องทำ (Tasks/Activities)
• แท่งบาร์ (Bars): เริ่มต้นที่จุดเริ่ม (Start) และสิ้นสุดที่จุดจบ (Finish) ความยาวของแท่งเท่ากับ ระยะเวลา (Duration)

2. หมุดหมายสำคัญ (Milestone ◆)

⭐ ออกสอบชัวร์

• กฎเหล็ก: Milestone คือ "เหตุการณ์หรือจุดส่งมอบสำคัญที่ ไม่มีระยะเวลาทำงาน (Duration = 0) และไม่ใช้ทรัพยากร"
• สัญลักษณ์: ใช้รูป สี่เหลี่ยมข้าวหลามตัด (Diamond ◆) บน Gantt Chart
• ตัวอย่าง: วันลงนามสัญญา, วันส่งมอบซอฟต์แวร์รอบแรก, วันเปิดตัวระบบจริง (Go-Live)

3. ความสัมพันธ์ระหว่างงาน (Dependencies)

Finish-to-Start

• เส้นลูกศรเชื่อมระหว่างบาร์ เพื่อระบุว่างานไหนต้องเสร็จก่อน งานไหนถึงจะเริ่มได้
• รูปแบบพื้นฐานที่สุดคือ Finish-to-Start (FS): งาน A ต้องเสร็จสมบูรณ์ก่อน งาน B จึงจะสามารถเริ่มทำได้
• งานที่ไม่มีงานก่อนหน้า (Predecessor = -) สามารถเริ่มต้นได้ทันทีพร้อมกัน (Parallel)

4. ช่วงเวลาลอยตัว (Slack / Float Bar)

ความยืดหยุ่น

• แถบประต่อท้ายแท่งงาน แสดง Slack Time (LS - ES)
• ช่วยให้ผู้จัดการโครงการรู้ว่างานนี้ "สามารถเลื่อนออกไปได้กี่วัน โดยไม่ส่งผลกระทบต่อวันเสร็จสิ้นของโครงการรวม"
• ส่วนงานที่อยู่บน Critical Path จะไม่มีแถบประนี้เลย (Slack = 0)

⚖️ ส่วนที่ 4: อ่านทำความเข้าใจ • ตารางเปรียบเทียบมหากาพย์ Gantt Chart vs PERT/CPM

เปรียบเทียบ 6 มิติสำคัญ (โจทย์ชอบออกถามข้อดี-ข้อจำกัด):

อาจารย์มักนำมาออกสอบข้อเขียนว่า "Gantt Chart กับ PERT/CPM แตกต่างกันอย่างไร และเมื่อไหร่ควรใช้เครื่องมือใด?" จำตารางนี้ไปตอบได้คะแนนเต็มแน่นอน:

มิติการเปรียบเทียบ 📊 Gantt Chart (แผนภูมิแกนต์) 🕸️ PERT / CPM (แผนผังเครือข่าย AON)
1. ลักษณะกราฟิก แผนภูมิแท่งแนวนอน (Horizontal Bar Chart) วางเรียงตามปฏิทินเวลาจริง แผนผังเครือข่าย (Network Diagram) เชื่อมโยงด้วยโหนด (Nodes) และลูกศรแสดงทิศทาง
2. จุดเด่นที่สุด เห็น ปฏิทินไทม์ไลน์ (Timeline) และความคืบหน้า (Progress) ของงานแต่ละชิ้นได้ชัดเจนมากที่สุด แสดง ความสัมพันธ์ระหว่างกิจกรรม (Dependencies) และคำนวณหาสายงานวิกฤตได้แม่นยำที่สุด
3. การดูสายงานวิกฤต (Critical Path) ดูยากในระดับสายตา ต้องใช้การไฮไลต์สีแท่งพิเศษ จึงจะสังเกตเห็น ดูง่ายและชัดเจนมาก เพราะคำนวณด้วยสูตรคณิตศาสตร์ (ES, EF, LS, LF) และเชื่อมต่อเส้นทาง Slack = 0
4. การดูเวลาลอยตัว (Slack Time) แสดงได้ยาก หากไม่วาดแถบประต่อท้ายแท่งงาน คำนวณออกมาเป็นตัวเลขชัดเจนในทุกกล่องโหนด (Slack = LS - ES)
5. ความเหมาะสมในการนำเสนอ เหมาะมากสำหรับนำเสนอ ผู้บริหารระดับสูง (Executive), ลูกค้า หรือคณะกรรมการ เพราะเข้าใจง่าย สวยงาม ใครดูก็รู้เรื่อง เหมาะสำหรับ ผู้จัดการโครงการ (Project Manager), วิศวกร และทีมพัฒนา ใช้ควบคุมงานเทคนิคหลังบ้าน
6. ข้อจำกัดเมื่อโครงการมีขนาดใหญ่ หากมีกิจกรรมมากกว่า 50-100 กิจกรรม แท่งจะยาวและแออัดมาก มองไม่เห็นว่างานไหนกระทบงานไหน สามารถรองรับโครงสร้างโครงการที่มีความซับซ้อนสูงและการแตกแขนงของงานหลายร้อยงานได้ดีกว่า

💡 สูตรลัดจับประเด็นในห้องสอบ:

• ถ้าโจทย์ถามว่า "ต้องการสื่อสารตารางเวลากับลูกค้า หรือรายงานสถานะโครงการให้บอร์ดบริหารดู ควรใช้เครื่องมือใด?" -> ตอบ: Gantt Chart
• ถ้าโจทย์ถามว่า "ต้องการคำนวณหาระยะเวลาโครงการที่สั้นที่สุด และหากิจกรรมที่ห้ามล่าช้าเด็ดขาด ควรใช้เครื่องมือใด?" -> ตอบ: PERT / CPM
• ถ้าโจทย์ถามว่า "Milestone แตกต่างจาก Activity ทั่วไปอย่างไร?" -> ตอบ: Milestone มี Duration = 0 ไม่ใช้ทรัพยากร มักแทนด้วยสัญลักษณ์สี่เหลี่ยมข้าวหลามตัด (Diamond ◆)
⚠️ จุดที่เด็กชอบพลาดจนเสียคะแนนในเรื่อง Critical Path

❌ สับสนเรื่อง MAX กับ MIN: จำให้แม่นว่า "ขาเดินหน้าไปข้างหน้า ให้เลือกค่ามากสุด (MAX)" แต่ "ขาถอยหลังกลับมา ให้เลือกค่าน้อยสุด (MIN)"

❌ ลืมคำนวณ Slack ให้ครบทุกช่อง: เวลาเขียนตารางส่งอาจารย์ ต้องมีคอลัมน์ Slack ชัดเจน และโชว์ว่างานบน Critical Path มี Slack เป็น 0

❌ ลืมเขียนสรุปประโยคสุดท้าย: ต้องเขียนระบุชัดเจนเสมอว่า "Critical Path คือเส้นทาง... รวมระยะเวลา... วัน"

Data Flow Diagram (DFD) & กฎเหล็ก 3 ข้อ

การจำลองการไหลของข้อมูล: Context Diagram ต่างจาก Diagram 0 อย่างไร -> 3 ข้อผิดพลาดร้ายแรง -> กฎห้ามลากเส้นข้าม

📖 ส่วนที่ 1: อ่านทำความเข้าใจ • Context Diagram ต่างจาก Diagram 0 อย่างไร?
1. Context Diagram (Level 0 DFD)

• คือ "ภาพมุมมองสูงสุดของระบบ (Bird's Eye View)"
• มี Process เพียงวงกลมเดียวตรงกลาง (Process 0) แทนทั้งระบบ เช่น "Food Ordering System"
• รอบๆ มีเฉพาะ External Entity (เช่น ลูกค้า, ครัว, ธนาคาร) ส่งข้อมูลเข้า/ออก
• ⚠️ กฎเหล็ก: ห้ามมี Data Store (คลังข้อมูล) โผล่มาใน Context Diagram เด็ดขาด!

2. Diagram 0 (Level 1 DFD)

• คือการ "ระเบิดขยายรายละเอียดข้างใน Process 0 ออกมา (Explosion)"
• แตกเป็น Process ย่อยๆ ที่มีเลขกำกับ เช่น 1.0 รับออเดอร์, 2.0 คิดเงิน, 3.0 ตัดสต็อก
• ✔️ มี Data Store (D1, D2 เช่น แฟ้มข้อมูลสินค้า, แฟ้มคำสั่งซื้อ) ปรากฏได้ในระดับนี้

📊 ส่วนที่ 2: ตัวอย่างจริง • Context Diagram vs Diagram 0 (ระบบสั่งอาหาร)

ผังแสดงการไหลของข้อมูล • Context Diagram (Level 0)

ภาพรวมระดับสูงสุด: มีเพียง Process 0 วงกลมเดียวตรงกลาง เชื่อมกับ Entity ภายนอก (ห้ามมี Data Store เด็ดขาด)

⚖️ กฎความสมดุล (Level Balancing Checklist ที่อาจารย์ใช้ตรวจข้อสอบ):
• Input ขาเข้าจาก Entity: ใน Context Diagram มี Order Details จาก Customer -> ใน Diagram 0 ก็ต้องไหลเข้า Process ย่อยครบถ้วน
• Output ขาส่งออกไป Entity: ใน Context Diagram มี Order Slip ส่งให้ Kitchen และ Receipt / Food ส่งกลับให้ Customer -> ใน Diagram 0 ต้องส่งออกให้ Entity เดิมห้ามตกหล่น!
• สิ่งที่เพิ่มเข้ามาเฉพาะใน Diagram 0: เริ่มมีเลขกระบวนการย่อย 1.0, 2.0, 3.0 และมี Data Store D1, D2 เพื่อจัดเก็บข้อมูล (ซึ่งใน Context Diagram ถูกซ่อนไว้ข้างใน)
⚠️ ส่วนที่ 3: กฎเหล็ก 3 ข้อผิดพลาดร้ายแรง (DFD Errors) ที่ห้ามวาด

3 ข้อผิดพลาดที่อาจารย์หักคะแนนหนักที่สุด:

🕳️ 1. Black Hole (หลุมดำ)

อาการ: Process มีแต่ลูกศรไหลเข้า (Inputs) แต่ไม่มีลูกศรไหลออก (Outputs) เลยแม้แต่เส้นเดียว!

เหมือนทิ้งข้อมูลลงหลุมดำ ระบบประมวลผลแล้วไม่ได้ส่งอะไรให้ใครเลย ถือว่าผิดหลักการทำงานของระบบสารสนเทศ

✨ 2. Miracle (ปาฏิหาริย์)

อาการ: Process มีแต่ลูกศรส่งออก (Outputs) แต่ไม่มีข้อมูลไหลเข้า (Inputs) เลย!

จู่ๆ ระบบก็เสกข้อมูลส่งออกไปเองได้โดยไม่รับข้อมูลต้นทางเข้ามา ถือเป็นปาฏิหาริย์ที่ผิดหลักการ

🌫️ 3. Gray Hole (หลุมเทา)

อาการ: ข้อมูลขาเข้าไม่เพียงพอที่จะสร้างข้อมูลขาออกได้

เช่น รับเข้ามาแค่ "รหัสพนักงาน" แต่ขาส่งออกกลับสร้าง "รายงานยอดขายประจำปี" ซึ่งข้อมูลขาเข้าไม่สมเหตุสมผล

กฎเหล็กการลากเส้นเชื่อมโยง (ห้ามลากข้ามเด็ดขาด):
1. ❌ ห้ามลาก Entity -> Entity โดยตรง (ต้องส่งผ่าน Process เสมอ)
2. ❌ ห้ามลาก Entity -> Data Store โดยตรง (ลูกค้าเดินไปเปิดแฟ้มข้อมูลเองไม่ได้ ต้องผ่าน Process)
3. ❌ ห้ามลาก Data Store -> Data Store โดยตรง (แฟ้มข้อมูลคุยกันเองไม่ได้ ต้องมี Process มาดึงข้อมูล)
CSC481 • ข้อที่ 6 (10 คะแนนเต็ม) • อิงจากไฟล์เอกสาร SWOT_FishBone2.pdf

Fishbone Diagram (ผังก้างปลา) & การพิชิตโจทย์ข้อสอบจริง

ถอดรหัสจากเอกสารสไลด์อาจารย์ (SWOT_FishBone2.pdf): วิเคราะห์ปัญหายอดขายลดลง/ทิ้งตะกร้าสินค้า -> ขุดรากเหง้าด้วย 5 Whys -> วาดผังก้างปลา -> เขียน Action Plan คะแนนเต็ม 10/10

🎯 หัวใจห้องสอบ • 3 สเต็ปเปลี่ยน "โจทย์ข้อสอบ 1 ย่อหน้า" เป็น "ผังก้างปลา 10 คะแนนเต็ม"

กรณีที่อาจารย์ให้โจทย์สถานการณ์ (Problem Scenario) มา ให้อ่านและทำตามลำดับนี้ทันที:

📍 สเต็ปที่ 1: วงกลมหา "หัวปลา" (Effect)

กวาดสายตาหา "ผลกระทบสุดท้ายเชิงลบหรือตัวเลขวิกฤต" ในโจทย์ เช่น ยอดขายลดลง, อัตราการซื้อสำเร็จต่ำ (Conversion Rate ต่ำ), ลูกค้าทิ้งตะกร้าสินค้า
⚠️ กฎเหล็ก: ห้ามเอาวิธีแก้ (เช่น "ต้องทำระบบใหม่") ไปใส่หัวปลาเด็ดขาด! หัวปลา = ปัญหาที่เกิดขึ้นแล้วเท่านั้น

🦴 สเต็ปที่ 2: เลือกกรอบ "ก้างใหญ่" (Major Bones)

อิงตามสไลด์อาจารย์ (SWOT_FishBone2.pdf หน้า 7-8) สำหรับโจทย์ E-Commerce / Digital Business ให้ใช้ 4-5 ด้านนี้เป็นหลัก:
• 1. ระบบและเทคโนโลยี (System & Technology)
• 2. ผลิตภัณฑ์และราคา (Product & Pricing)
• 3. การบริการและขนส่ง (Service & Logistics)
• 4. การตลาดและการสื่อสาร (Marketing & Promotion)
• (และปัจจัยภายนอก External Factors)

🔍 สเต็ปที่ 3: แตก "ก้างย่อย" ด้วย 5 Whys

นำข้อความที่โจทย์บ่นหรือปัญหาที่โจทย์บอกมาแยกใส่ก้างใหญ่ แล้วถามต่อว่า "ทำไมสิ่งนี้ถึงเกิดขึ้น?" ลึกลงไป 2-3 ชั้น เพื่อหารากเหง้าเชิงระบบ เช่น เว็บโหลดช้า -> รูปใหญ่ไม่บีบอัด -> ขาด CDN กระจายโหลด นำรากเหง้านี้ไปเขียนเป็นก้างย่อย

📖 ส่วนที่ 1: ถอดรหัสโจทย์ข้อสอบจริง • วิเคราะห์รากเหง้าตามสไลด์อาจารย์ (SWOT_FishBone2.pdf หน้า 7)
🏢 สถานการณ์จำลองข้อสอบจริง (จากไฟล์ SWOT_FishBone2.pdf):

"ปัญหายอดฮิตในธุรกิจ E-Commerce: ร้านค้าออนไลน์พบว่า ยอดขายลดลง และอัตราการซื้อสำเร็จต่ำ (Low Sales Conversion Rate) ลูกค้าเลือกของใส่ตะกร้าแต่กดปิดหนี (Cart Abandonment) สูง จากการวิเคราะห์พบปัญหา 4 ด้าน: หน้าเว็บโหลดช้าเกิน 3 วินาที และขั้นตอน Checkout ซับซ้อนบังคับสมัครสมาชิกก่อนซื้อ, สินค้าหมดสต็อกบ่อยและราคาแพงกว่าคู่แข่ง, ค่าจัดส่งแพงเกินไป ไม่มีเก็บเงินปลายทาง (COD) และแอดมินตอบแชตช้า, รวมถึงลูกค้าที่ทิ้งตะกร้าสินค้าไม่ได้รับการติดตามกระตุ้นให้กลับมาซื้อ"

🎯 หัวปลา (Effect ที่สกัดได้): ยอดขายลดลง / อัตราการซื้อสำเร็จต่ำ (Conversion Rate ต่ำ) 🧩 กรอบการวิเคราะห์: 4 หมวดหมู่ E-Commerce ตามสไลด์วิชา CSC481

เมื่อได้ปัญหาหลักแล้ว เรานำอาการในโจทย์มาจัดหมวดหมู่และขุดลึกด้วยเทคนิค "5 Whys (ถามทำไม 5 ครั้ง)" เพื่อหารากเหง้าที่แท้จริงในแต่ละด้าน (ตรงตามสไลด์อาจารย์หน้า 7):

💻 1. ด้านระบบและเทคโนโลยี (System & Technology)

System / Infra

• เว็บไซต์/แอป โหลดช้า (> 3 วินาที):
ทำไมช้า? -> ไฟล์รูปภาพสินค้ามีขนาดใหญ่เกินไป ไม่ได้บีบอัด และไม่มี CDN แคชไฟล์
💡 รากเหง้า: ขาด Cloudflare CDN และไม่ได้แปลงไฟล์เป็นสกุล .webp

• ขั้นตอนการชำระเงิน (Checkout) ซับซ้อน & บังคับสมัครสมาชิก:
ทำไมลูกค้าปิดหนี? -> ต้องกรอกข้อมูลหลายขั้นตอน เสียเวลารอรับรหัส OTP
💡 รากเหง้า: ขาดระบบ One-Page Checkout และระบบ Guest Checkout

📦 2. ด้านผลิตภัณฑ์และราคา (Product & Pricing)

Product & Value

• สินค้าหมดสต็อกบ่อย (Out of Stock) & รูปภาพไม่ชัดเจน:
ทำไมของหมดไม่รู้ตัว? -> สต็อกหน้าร้านกับออนไลน์ไม่ซิงค์กัน ขาดระบบตัดสต็อก Real-time
💡 รากเหง้า: ขาดระบบเชื่อมโยงคลังสินค้า ERP/WMS และขาดรีวิวจากผู้ใช้จริง

• ราคาสูงกว่าคู่แข่ง:
ทำไมลูกค้าไปซื้อร้านอื่น? -> ขาดความคุ้มค่าที่แตกต่างเมื่อเทียบกับราคาที่ต้องจ่าย
💡 รากเหง้า: ขาดการจัดเซ็ตสินค้าสุดคุ้ม (Product Bundling) เพื่อชูคุณค่าแทนการตัดราคา

🚚 3. ด้านการบริการและขนส่ง (Service & Logistics)

Service & Trust

• ค่าจัดส่งแพงเกินไป & ไม่มีเก็บเงินปลายทาง (COD):
ทำไมลูกค้าทิ้งตะกร้า? -> สาเหตุหลักอันดับ 1 ของ Cart Abandonment คือเจอบวกค่าส่งแพง และลูกค้าใหม่ไม่กล้าโอนเงินก่อน
💡 รากเหง้า: ขาดโปรโมชันส่งฟรี และขาดช่องทางชำระเงินปลายทาง (COD)

• แอดมินตอบแชตช้า:
ทำไมตอบช้า? -> ลูกค้าทักถามพร้อมกันจำนวนมากในคำถามซ้ำๆ (ของพร้อมส่งไหม, ค่าส่งเท่าไร)
💡 รากเหง้า: ขาดระบบ AI Chatbot คอยตอบคำถามอัตโนมัติ 24 ชม.

📢 4. ด้านการตลาดและการสื่อสาร (Marketing & Promotion)

Marketing & Retargeting

• ขาดการทำ Retargeting (ไม่ติดตามลูกค้าที่ทิ้งตะกร้า):
ทำไมยอดขายหลุดลอย? -> ลูกค้าเลือกของใส่ตะกร้าไว้แล้วหลุดไป แต่ร้านค้าไม่มีการส่งข้อความเตือน
💡 รากเหง้า: ขาดระบบ Abandoned Cart Retargeting บรอดแคสต์เตือนพร้อมโค้ดส่วนลด

• การยิงโฆษณาไม่ตรงกลุ่มเป้าหมาย & โปรโมชันไม่ดึงดูด:
ทำไมคนเข้าเว็บเยอะแต่ไม่ซื้อ? -> ดึงดูดได้เฉพาะ Traffic ที่ไม่มีความสนใจซื้อจริง
💡 รากเหง้า: ขาดการใช้ Custom / Lookalike Audience ในการยิงแอด

📊 ส่วนที่ 2: ผังก้างปลาที่สมบูรณ์ (Visual Fishbone Diagram จากสไลด์อาจารย์ หน้า 8)

จำลองกราฟิกผังก้างปลาจากเอกสารประกอบการสอน SWOT_FishBone2.pdf (หน้า 8) อย่างครบถ้วนทุกก้างและก้างย่อย โดยคุมโค้ดสีตรงกับส่วนที่ 1 และหัวปลาชี้ทางขวา:

1. ระบบและเทคโนโลยี (ฟ้า) 2. ผลิตภัณฑ์และราคา (เขียว) 3. การบริการและขนส่ง (ม่วง) 4. การตลาดและการสื่อสาร (ส้มทอง) ปัญหาหลัก (แดง)
✍️ ส่วนที่ 3: วิธีเขียนตอบในห้องสอบ (Exam Action Plan Blueprint จากสไลด์หน้า 12-13)

กระดาษคำตอบแผนปฏิบัติการแก้ไขปัญหา (Action Plan) ที่ได้คะแนนเต็ม 10/10:

เมื่อวาดผังก้างปลาเสร็จ อาจารย์มักจะให้เขียน "แนวทางการแก้ไขปัญหา (Solutions & Action Plan)" ให้แบ่งตอบตรงตามหมวดหมู่ก้างปลา โดยระบุเครื่องมือและวิธีแก้ที่ชัดเจน (ถอดรหัสจากสไลด์อาจารย์หน้า 12-13):

💻 1. แก้ไขด้านระบบและเทคโนโลยี (System & Technology):
  • ⚡ ลดเวลาโหลดเว็บ/แอป: บีบอัดขนาดไฟล์ภาพ (ใช้ไฟล์ .webp แทน .png/jpeg) และใช้ CDN (Content Delivery Network) ช่วยกระจายการโหลด ให้เปิดหน้าสินค้าได้ภายใน 1-2 วินาที
  • ⚡ ปรับเป็น One-Page Checkout: ลดขั้นตอนการสั่งซื้อให้ลูกค้าชำระเงินในหน้าเดียว และเปิดระบบ Guest Checkout ซื้อได้ทันทีโดยไม่ต้องบังคับลงทะเบียนหรือยืนยัน OTP ซ้ำซ้อน
  • 🚀 อัปเกรด Server รองรับ Flash Sale: ใช้ Cloud Server ที่ปรับขนาดทรัพยากรอัตโนมัติ (Auto-scaling) เพื่อรองรับทราฟฟิกช่วงแคมเปญใหญ่
📦 2. แก้ไขด้านผลิตภัณฑ์และราคา (Product & Pricing):
  • ⚡ จัดการสต็อกด้วยระบบ Real-time: ใช้ระบบ ERP/WMS เชื่อมสต็อกทุกช่องทาง ป้องกันสินค้าหมดสต็อก และเพิ่มระบบ "แจ้งเตือนเมื่อมีสินค้า" (Back in Stock Alert)
  • ⚡ ชูคุณค่าแทนการตัดราคา: หากลดราคาไม่ได้ ให้จัดเซ็ตสุดคุ้ม (Product Bundling), แถมของขวัญ หรือให้สะสมแต้มเพื่อสร้าง Value for Money
  • 🚀 PDP Optimization & Social Proof: ใช้รูปภาพความละเอียดสูง วิดีโอรีวิวการใช้งานจริง ใส่ Size Chart ชัดเจน และแสดงรีวิวจากผู้ใช้จริงติดป้าย "ของแท้ 100%"
🚚 3. แก้ไขด้านการบริการและขนส่ง (Service & Logistics):
  • ⚡ แก้ปัญหาค่าส่งด้วยโปรโมชัน: กำหนดเกณฑ์ "ส่งฟรีเมื่อซื้อครบ X บาท" (Free Shipping Threshold) เพื่อกระตุ้นยอดซื้อต่อบิล (AOV) และลดอัตราการทิ้งตะกร้าสินค้า
  • ⚡ เพิ่มช่องทางชำระเงินให้ครอบคลุม: เปิดรับบริการ เก็บเงินปลายทาง (COD), ผ่อนชำระ 0%, และ Buy Now Pay Later (BNPL) เพื่อสร้างความมั่นใจให้ผู้ซื้อหน้าใหม่
  • 🚀 ใช้งาน Chatbot ช่วยแอดมิน: ติดตั้ง AI Chatbot ตอบคำถามยอดฮิต (FAQ) อัตโนมัติ 24 ชม. และใช้ระบบแจ้งเตือนให้แอดมินตอบแชตเคสพิเศษได้เร็วที่สุดภายใน 3-5 นาที
📢 4. แก้ไขด้านการตลาดและการสื่อสาร (Marketing & Promotion):
  • ⚡ ทำ Abandoned Cart Retargeting: ส่งข้อความบรอดแคสต์หรือยิงโฆษณาเตือนคนที่ทิ้งตะกร้าสินค้าค้างไว้ พร้อมมอบโค้ดส่วนลดพิเศษเพื่อปิดการขายทันที
  • 🚀 ปรับ Targeting ด้วย Custom/Lookalike Audience: ยิงโฆษณาหาคนที่เคยซื้อสินค้า หรือคนที่กำลังมองหาสินค้าประเภทเดียวกัน เพื่อดึง Traffic คุณภาพสูงที่มีกำลังซื้อจริง
⚠️ ส่วนที่ 4: กับดักข้อสอบ & จุดที่นักศึกษาชอบทำผิด (จุดหักแต้มยอดฮิต)

❌ จุดผิดที่ 1: เขียน "วิธีแก้" ไว้ที่หัวปลา! (โดนหัก 0 ทันที)
นักศึกษาหลายคนเผลอเขียนที่หัวปลาว่า "ต้องปรับปรุงเว็บไซต์ให้เร็วขึ้น" หรือ "ต้องเพิ่มระบบ One-Page Checkout" — ผิดหลักการอย่างรุนแรง!
จำไว้เสมอ: หัวปลาต้องเป็น "ปัญหาหรือผลกระทบเชิงลบที่เกิดขึ้นแล้ว (Effect)" เท่านั้น เช่น "ยอดขายลดลง / อัตราการซื้อสำเร็จต่ำ"

❌ จุดผิดที่ 2: นำกรอบ 4M โรงงานมาฝืนใช้กับระบบ IT
โจทย์ระบบสารสนเทศ / เว็บไซต์ / ซอฟต์แวร์ ถ้าไปใช้ Man, Machine, Material, Method จะไม่มีช่องสำหรับเรื่อง ราคา & นโยบาย (Price/Policy) และ ระบบไอที (Platform) ทำให้นักศึกษาเสียคะแนนการวิเคราะห์ไปฟรีๆ

❌ จุดผิดที่ 3: ก้างหลักและก้างย่อยไม่สอดคล้องกัน (Misclassification)
เช่น นำเรื่อง "แอดมินตอบแชตช้า" ไปใส่ไว้ใต้ก้าง "ระบบและเทคโนโลยี" (ทั้งที่เป็นเรื่องของ "การบริการ") ตรวจสอบให้ตรงหมวดหมู่อยู่เสมอ

❌ จุดผิดที่ 4: ใน Action Plan เขียนวิธีแก้แบบกว้างๆ ลอยๆ
เช่น เขียนแค่ว่า "พัฒนาระบบให้ดีขึ้น" หรือ "ตั้งใจบริการลูกค้า" แบบนี้อาจารย์ไม่ให้คะแนน! ต้องระบุแนวทางเชิงเทคนิคหรือขั้นตอนปฏิบัติที่จับต้องได้ เช่น "บีบอัดภาพเป็น .webp + ทำ Cloudflare CDN", "เพิ่ม One-Page Guest Checkout", "ทำ Abandoned Cart Retargeting"

🧪 ข้อที่ 1 • Normalization (1NF ➔ 3NF & BCNF) [15 คะแนน]
• 1NF: กำจัด Repeating Groups (กลุ่มข้อมูลซ้ำ) -> ทุกช่องเป็นค่าเดี่ยว (Atomic Values) -> ขีดเส้นใต้ Composite PK (มักมี 2 ตัว เช่น StudentID, CourseID)
• 2NF: กำจัด Partial Dependency (ฟิลด์ธรรมดาแอบขึ้นกับ PK แค่ตัวใดตัวหนึ่ง) -> แตกฟิลด์นั้นออกไปสร้างตารางใหม่พร้อมยก PK ตัวที่มันขึ้นตรงด้วยไปเป็น Primary Key
• 3NF: กำจัด Transitive Dependency (A -> B -> C ฟิลด์ธรรมดาแอบขึ้นตรงกับฟิลด์ธรรมดาด้วยกันเอง เช่น Zipcode -> Province) -> แตกออกเป็นตารางใหม่ ทิ้ง FK ไว้เชื่อม
• BCNF: ทุกตัวที่เป็น Determinant (ตัวระบุค่าคนอื่น) จะต้องมีสถานะเป็น Candidate Key เสมอ!
📐 ข้อที่ 2 • สัญลักษณ์ ER Diagram & Crow's Foot [15 คะแนน]
• รูปทรงพื้นฐาน: สี่เหลี่ยม = Entity | วงรี = Attribute | สี่เหลี่ยมซ้อน 2 ชั้น = Weak Entity (เอนทิตีอ่อนแอ อยู่ตามลำพังไม่ได้ เช่น บุตรพนักงาน)
• ประเภท Attribute:
    • ขีดเส้นใต้ทึบ = Primary Key
    • ขีดเส้นใต้ประ = Partial Key / Discriminator (คีย์จำแนกใน Weak Entity)
    • วงรีซ้อน 2 ชั้น ((...)): Multi-valued Attribute (มีได้หลายค่า เช่น เบอร์โทร, ทักษะ)
    • วงรีเส้นประ (--...--): Derived Attribute (คำนวณมาจากฟิลด์อื่นได้ เช่น อายุ คำนวณจากวันเกิด)
    • กิ่งก้านแตกออก: Composite Attribute (แตกเป็นส่วนย่อยได้ เช่น ชื่อ-นามสกุล, ที่อยู่)
• สัญลักษณ์ปลายเส้น Crow's Foot:
    • || = Mandatory One (ต้องมี 1 และมีได้แค่ 1 เดียว)
    • O| = Optional One (จะมีหรือไม่มีก็ได้ ไม่เกิน 1)
    • |{ = Mandatory Many (ต้องมีอย่างน้อย 1 และมีได้หลายรายการ)
    • O{ = Optional Many (จะมีหรือไม่มีก็ได้ และมีได้หลายรายการ)
🔄 ข้อที่ 3 • แปลง ERD เป็นตาราง (Relational Schema) [15 คะแนน]
• 1:M (หนึ่ง ต่อ กลุ่ม): เอา PK ฝั่ง 1 ไปเป็น Foreign Key (FK) ให้ฝั่ง Many (ท่อง: "ลูกดึงบัตรแม่มาถือ")
• M:N (กลุ่ม ต่อ กลุ่ม): ต้องสร้างตารางกลาง (Bridge Table / Junction Table) เสมอ! เช่น ASSIGNMENT(EmpID, ProjectID, Hours)
    👉 ดึง PK ทั้งสองฝั่งมารวมเป็น Composite PK (และทำหน้าที่เป็น FK ด้วย)
    👉 จุดห้ามลืม: ถ้ามี Attribute บนเส้นความสัมพันธ์ (เช่น Hours, Grade) ให้ดึงมาใส่ในตารางกลางนี้!
• 1:1 (หนึ่ง ต่อ หนึ่ง): เอา PK ฝั่งที่มี Total Participation (ฝั่งที่จำเป็นต้องมี) ไปเป็น FK ของอีกฝั่ง หรือรวมเป็นตารางเดียว
• Multi-valued Attribute: ต้องแตกเป็นตารางใหม่ โดยมี PK ของตารางหลักเป็น FK + ดึงตัวมันเองมารวมเป็น Composite PK
🔑 ข้อที่ 4 • ชนิดของ Keys & กฎความสมบูรณ์ [15 คะแนน]
• ความต่างของ Keys:
    • Super Key: กลุ่มของฟิลด์ที่ระบุแถวได้ไม่ซ้ำ (อาจมีฟิลด์แถมฟุ่มเฟือยได้)
    • Candidate Key: Super Key ขั้นต่ำที่ตัดของแถมออกหมดแล้ว พร้อมเป็น PK ได้ทุกตัว
    • Primary Key (PK): ตัวแทนที่ถูกเลือกให้เป็นคีย์หลักเพียงหนึ่งเดียว (ห้าม NULL และห้ามซ้ำ)
    • Alternate Key: Candidate Key ตัวสำรองที่ไม่ถูกเลือกเป็น PK
    • Foreign Key (FK): คีย์นอกที่ชี้ไปยัง Primary Key ของอีกตารางหนึ่ง
• กฎความสมบูรณ์ 2 ข้อหลัก (Integrity Rules):
    1. Entity Integrity Rule: ค่าของ Primary Key ห้ามเป็น NULL และห้ามมีค่าซ้ำโดยเด็ดขาด
    2. Referential Integrity Rule: ค่าของ Foreign Key จะต้องตรงกับค่า Primary Key ในตารางแม่ที่มีอยู่จริง หรือเป็นค่า NULL เท่านั้น (ห้ามมีข้อมูลกำพร้า / Orphan Records)

⏱️ ข้อที่ 4 • คำนวณ Critical Path Method (CPM) & Gantt Chart [10 คะแนน ออกชัวร์ 100%]
• โครงสร้างกล่องโหนด 6 ช่อง: [ES | Dur | EF] / [LS | Slack | LF]
• 1. Forward Pass (เดินหน้าซ้าย ➔ ขวา): EF = ES + Duration
    👉 จุดระวัง: ถ้ามีลูกศรวิ่งชนโหนดปลายทางมากกว่า 1 เส้น ให้เลือกค่า มากที่สุด (MAX) เสมอ!
• 2. Backward Pass (ถอยหลังขวา ➔ ซ้าย): LS = LF - Duration
    👉 เริ่มต้นให้ LF ของงานสุดท้าย = เวลารวมโครงการ (EF ล่าสุด)
    👉 จุดระวัง: ถ้างานหนึ่งส่งให้หลายงานข้างหลัง ให้เลือกค่า LS ที่ น้อยที่สุด (MIN) ย้อนกลับมา!
• 3. Slack (เวลาลอยตัว): Slack = LS - ES (หรือ LF - EF ได้เท่ากันเป๊ะ)
    👉 Critical Path (สายงานวิกฤต): คือเส้นทางของงานที่ Slack = 0 ทุกตัวเชื่อมกัน และเวลารวมคือเวลาโครงการ
• Gantt Chart vs PERT/CPM (ประเด็นข้อสอบ):
    • Gantt Chart: แผนภูมิแท่งแนวนอน เห็นปฏิทินเวลา (Timeline/Progress) ชัดเจน เหมาะนำเสนอผู้บริหาร/ลูกค้า
    • PERT/CPM: ผังเครือข่าย คำนวณ Critical Path และ Slack ได้แม่นยำ เหมาะกับทีมวิศวกร/ควบคุมงาน
    • Milestone (หมุดหมายสำคัญ): กิจกรรมที่มี Duration = 0 ไม่ใช้ทรัพยากร มักแทนด้วยสัญลักษณ์สี่เหลี่ยมข้าวหลามตัด (Diamond ◆)
🌊 ข้อที่ 5 • Data Flow Diagram (DFD) & กฎเหล็ก [10 คะแนน ออกชัวร์ 100%]
• Context Diagram (Level 0): ภาพรวมสูงสุด มี Process 0 วงเดียว ตรงกลาง และ ห้ามมี Data Store (คลังข้อมูล) เด็ดขาด!
• Diagram 0 (Level 1 Explosion): ระเบิด Process 0 แตกเป็น Process ย่อย 1.0, 2.0, 3.0 และ มี Data Store (D1, D2...) โผล่มาได้
• Level Balancing: เส้นไหลเข้า-ออกจาก External Entity ระหว่าง Context Diagram กับ Diagram 0 ต้องตรงกันเป๊ะ 100%
• 3 ข้อผิดพลาดร้ายแรง (DFD Errors):
    1. 🕳️ Black Hole: Process มีแต่ Input เข้า แต่ไม่มี Output ออก
    2. ✨ Miracle: Process เสก Output ออกเอง โดยไม่มี Input เข้า
    3. 🌫️ Gray Hole: ข้อมูลขาเข้าไม่เพียงพอที่จะคำนวณสร้างขาออกได้ (เช่น เข้าแค่ชื่อ แต่ออกยอดขาย)
• กฎห้ามลากเส้นข้าม: ทุกเส้นต้องเชื่อมกับ Process เสมอ! (ห้าม Entity-Entity, ห้าม Entity-DataStore, ห้าม DataStore-DataStore)
🐟 ข้อที่ 6 • ผังก้างปลา (Fishbone / Ishikawa) & แผนแก้ [10 คะแนน]
• หัวปลา: ต้องเป็น "ปัญหาหรือผลกระทบที่เกิดขึ้นแล้ว (Effect)" เท่านั้น (เช่น ยอดขายตกต่ำ 35%) ห้ามเขียนวิธีแก้ที่หัวปลาเด็ดขาด!
• ก้างหลัก (หมวดหมู่): ภาคบริการ/ธุรกิจมักใช้ 4P (People, Process, Platform/Tech, Price/Policy) หรือภาคผลิตใช้ 4M/6M (Man, Machine, Material, Method, Mother nature)
• ก้างย่อย: หาสาเหตุรากเหง้า (Root Cause) โดยการถาม Why 5 ครั้ง (5 Whys Technique)
• Action Plan (แผนแก้ไข): เวลาตอบข้อสอบ ให้แบ่งตอบเป็น 4 ด้านตามก้างปลา โดยระบุทั้ง มาตรการด่วน (Immediate) และ แผนระยะยาว (Long-term)
📋 ข้อที่ 1, 2, 3 • SDLC, Feasibility, SWOT/TOWS, Fact-Finding [30 คะแนน]
• SDLC 5 ขั้นตอน: Planning (วางแผน) ➔ Analysis (วิเคราะห์ DFD/SRS) ➔ Design (ออกแบบ UI/ERD) ➔ Implementation (เขียนโค้ด/ทดสอบ UAT) ➔ Maintenance (บำรุงรักษา)
• Waterfall vs Agile:
    • Waterfall: ลำดับตายตัว ไม่ย้อนกลับ ปรับเปลี่ยนยาก เหมาะกับงานที่สเปกนิ่งแน่นอน
    • Agile (Scrum): แบ่งรอบ Sprint 2-4 สัปดาห์ ปรับเปลี่ยนตามความต้องการของลูกค้าได้รวดเร็ว
• Feasibility Study (TELOS 5 ด้าน):
    • T: Technical (เทคโนโลยีที่มีทำได้ไหม) | E: Economic (คุ้มค่าไหม ROI, Payback Period)
    • L: Legal (ถูกกฎหมาย/PDPA ไหม) | O: Operational (คนในองค์กรยอมรับและใช้เป็นไหม)
    • S: Schedule (สร้างเสร็จทันเวลาไหม)
• TOWS Matrix (กลยุทธ์ 4 ทิศทาง):
    • SO (เชิงรุก): ใช้จุดแข็ง (S) คว้าโอกาสภายนอก (O)
    • WO (เชิงปรับปรุง): แก้จุดอ่อน (W) เพื่อคว้าโอกาส (O)
    • ST (เชิงป้องกัน): ใช้จุดแข็ง (S) รับมือและหลบภัยคุกคาม (T)
    • WT (เชิงรับ/ถอย): ลดจุดอ่อน (W) และหลีกเลี่ยงภัยคุกคาม (T) เพื่อเอาชีวิตรอด
• Fact-Finding Techniques (การเก็บรวบรวมข้อมูล):
    • Interview: ได้ข้อมูลเชิงลึก สร้างความสัมพันธ์ แต่ใช้เวลานาน
    • Questionnaire: คนตอบได้เยอะ สรุปสถิติง่าย แต่ถามเจาะลึกไม่ได้
    • Observation: เห็นการทำงานหน้างานจริง แต่คนทำงานอาจเกร็ง (Hawthorne Effect)
    • JAD (Joint Application Development): ประชุมระดมสมองพร้อมกันทุกฝ่าย ได้ข้อสรุปรวดเร็ว
🚨 5 กับดักข้อสอบที่เด็กชอบพลาดจนตกม้าตาย (ท่องจำ 30 วินาทีสุดท้ายก่อนปิดกระเป๋า):
1. ❌ สับสน MAX vs MIN ใน CPM: ขาเดินหน้าไปข้างหน้า EF ให้เลือกค่า มากสุด (MAX) แต่ขาถอยหลังกลับ LS ให้เลือกค่า น้อยสุด (MIN) เท่านั้น!
2. ❌ ใส่ Data Store ใน Context Diagram: กฎเหล็กคือ Context Diagram มีได้แค่ Entity กับ Process 0 เท่านั้น ห้ามมีคลังข้อมูลเด็ดขาด
3. ❌ เขียนวิธีแก้ไว้ที่หัวปลา: หัวปลาต้องเป็น "ปัญหาหรือผลกระทบที่เกิดขึ้นแล้ว" เท่านั้น ไม่ใช่วิธีแก้ปัญหา
4. ❌ ลืมตาราง Bridge ในความสัมพันธ์ M:N: ห้ามเอา PK ไปใส่โต้งๆ ในตารางเดิม ต้องตั้งตารางกลางใหม่ (เช่น ASSIGNMENT) และดึงแอตทริบิวต์บนเส้นลงมาด้วยเสมอ
5. ❌ ลืมขีดเส้นใต้ Primary Key: เวลาเขียนผลลัพธ์ Normalization ส่งอาจารย์ ทุกตารางที่แตกออกมาต้องมี ขีดเส้นใต้ทึบ ที่ฟิลด์ Primary Key ให้ชัดเจนเสมอ
